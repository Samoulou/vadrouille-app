## Décision

### 1. Workflow `db-releve` (exigences : Sécu ; outillage : TL)

`.github/workflows/db-releve.yml`, livré par une PR de workflow (`owner-approved`, 0035), distincte de la PR du workflow `db-migrate` de 0056 :

- déclencheur `workflow_dispatch` seul, **sans `inputs`** ; `if: github.ref == 'refs/heads/main'` sur le job ; **environnement GitHub distinct `db-releve`** (règle de déploiement : `main` seule ; aucun relecteur), avec ses propres secrets `RELEVE_PGHOST`, `RELEVE_PGDATABASE` et `RELEVE_PGPASSWORD`, exposés à la seule étape du relevé ; `PGUSER: vadrouille_prototype_purge` écrit en clair. **L'environnement `p0-purge` et ses secrets ne sont pas utilisés** : 0046 (D16 point 7) les réserve à `p0-purge.yml`, et `tests/unit/ci/p0-purge.test.ts` (« l'environnement p0-purge n'est nommé que par p0-purge.yml ») le vérifie ; `db-releve.yml` ne nomme donc ni `p0-purge` ni `P0_PURGE_` (pas même en commentaire), ni `db-migrate` ni `MIGRATOR_`, et ni 0046 ni ce test ne sont amendés. Le mot de passe de `vadrouille_prototype_purge` est posé une seconde fois, dans `RELEVE_PGPASSWORD`, par qui la question ouverte 1 désigne ;
- **obtention de la copie** (mineur 1 du head `2010c68`) : les secrets GitHub sont en écriture seule, la valeur déjà posée dans `p0-purge` ne peut pas être relue. La copie n'est donc faite que **dans la même opération** qu'une pose du mot de passe selon S5 de 0046 : soit la pose initiale (si `p0-purge` n'a pas encore son secret), soit une **rotation** : nouveau mot de passe généré localement (`openssl rand -hex 32`), vérificateur SCRAM posé par `ALTER ROLE`, puis la même valeur transmise **par l'entrée standard** à `gh secret set --env p0-purge` et à `gh secret set --env db-releve`, jamais en argument ni affichée, la variable du processus effacée ensuite. **Toute rotation ultérieure du mot de passe de purge met à jour les deux environnements dans cette même opération** ; sinon l'un des deux workflows échoue à la connexion (échec fermé, sans fuite) ;
- `permissions: {}` ; `runs-on: ubuntu-24.04` ; **`timeout-minutes: 15`** (5 au head `37fffa4`, 10 au head `2010c68` : relevé au § 5.2, mineur 7) ; **`shell: bash`** sur l'étape (mineur 14 : GitHub lance alors `bash --noprofile --norc -eo pipefail {0}`, au lieu de `bash -e {0}` sans `pipefail` quand le shell n'est pas fixé) ; `concurrency: { group: db-releve, cancel-in-progress: false }` ; **aucune action, ni checkout** : le job n'a aucun fichier du dépôt ;
- `env:` de l'étape : `LC_ALL: C`, `PGHOST`, `PGDATABASE`, `PGPASSWORD` (les trois secrets ci-dessus), `PGUSER`, `PGSSLMODE: verify-full`, `PGSSLROOTCERT: system`, plus les textes SQL `SQL_SET`, `SQL_DO`, `SQL_BEGIN` et `SQL_R1` à `SQL_R8` (§ 3) ; aucune autre variable, ni `PG*`, ni `DATABASE_URL`, ni `VADROUILLE_DATABASE_URL*` ; **aucun `env:` au niveau du job ou du workflow** ;
- mêmes commandes interdites qu'au § 2.5 de 0056 (`eval`, `exec`, `trap`, `export`, `declare`, `let`, `(( ))`, `$(( ))`, toute commande qui charge un fichier, `psql -f`, entrée redirigée ou tube vers `psql`) ; **seules commandes externes admises : `psql -X` (connexion, § 3) et `psql --version` (§ 2)** ; une comparaison numérique ne porte que sur `${#…}` ; ni `set -x`, ni affichage de l'environnement.

### 2. Contrôles avant connexion (Sécu) — mineurs 4 et 5

Premiers dans l'étape, sans connexion, dans les mêmes formes qu'au § 2.6.1 de 0056 : `psql --version` de version majeure 16 ou plus (`sslrootcert=system`) — **seul appel admis sans `-X` ni `-v ON_ERROR_STOP=1`** (mineur 3 du head `2010c68`) : il ne lit pas `.psqlrc`, ne se connecte pas et n'exécute aucun SQL ; sa sortie n'est comparée qu'à `^psql \(PostgreSQL\) (1[6-9]|[2-9][0-9])\.` et n'est pas affichée ; `PGHOST` suit `^[a-z0-9.-]{1,253}$` et **ne contient pas `-pooler`** (hôte direct exigé : la session du § 3 enchaîne un `SET`, un bloc `DO` et une transaction que le pooler en mode transaction pourrait servir par des connexions serveur différentes ; le contrôle est un filet sur la convention de nommage de Neon, l'exigence restant celle de la question ouverte 1) ; `PGDATABASE` suit `^[a-z0-9_]{1,63}$`. **En cas d'échec de l'un de ces contrôles, le job n'affiche ni la valeur de `PGHOST` ni celle de `PGDATABASE`, ni une partie d'elles** (les journaux d'Actions d'un dépôt public sont publics) : il n'affiche que le nom du contrôle en échec, par un message fixe, et échoue sans connexion.

### 3. Rôle et session (Sécu)

- Rôle **`vadrouille_prototype_purge`** : il n'a qu'`EXECUTE` sur `prototype.purge_expired()` et `USAGE` sur le schéma `prototype` (`0003_prototype.sql`, lignes 514 à 518), aucun droit sur une table ; le relevé ne l'appelle pas.
- Une seule session `psql -X -v ON_ERROR_STOP=1 -A -t -F '|'` : `SET search_path = pg_catalog, pg_temp` ; puis, **en premier**, un bloc `DO` qui lève une exception si `session_user` ou `current_user` diffère de `vadrouille_prototype_purge`, si ce rôle a `rolsuper` ou `rolbypassrls`, ou si `ssl` est faux dans `pg_catalog.pg_stat_ssl` pour son processus, **et, dans le même bloc, si un nom ou une valeur que R1 à R8 affichent contient un caractère de contrôle** (bloquant 1 du head `2010c68`) : `~ '[[:cntrl:]]'` sur `pg_roles.rolname`, `pg_namespace.nspname`, `pg_class.relname`, `pg_attribute.attname`, `pg_proc.proname`, `pg_type.typname`, `pg_extension.extname`, `pg_extension.extversion` et `pg_proc.proconfig::text` (les ACL et `regprocedure` sont composés de ces noms) ; puis `BEGIN TRANSACTION READ ONLY` ; puis **exactement les requêtes R1 à R8** (§ 4), écrites en clair dans le YAML et approuvées avec lui. La session se termine sans `COMMIT` ; rien n'est écrit.
- **Envoi du SQL (TL ; mineur 2 du head `2010c68`)** : un seul appel `psql -X -v ON_ERROR_STOP=1 -A -t -F '|'` formé de **`-c` successifs, un par instruction, dans cet ordre** : `-c "$SQL_SET" -c "$SQL_DO" -c "$SQL_BEGIN" -c "$SQL_R1"` … `-c "$SQL_R8"` (forme de 0056, § 2.6.4 ; un `-c` est envoyé au serveur sans interprétation des méta-commandes ni des variables de `psql`). **Règle de guillemets** : chaque texte SQL est la valeur d'une variable de l'`env:` de l'étape, écrite en YAML (scalaire littéral `|` ou chaîne entre apostrophes YAML), jamais dans le bloc `run:` ; bash ne le reçoit que par `"$SQL_…"` entre guillemets, dont le contenu n'est pas réinterprété : les apostrophes des littéraux SQL (`'pg_proc'::regclass`, `'EXECUTE'`) et le `$$` du bloc `DO` restent tels quels, sans échappement propre au shell. Aucun texte SQL ne contient `${{` (aucune expression d'Actions). Le test statique compare chaque valeur, après analyse du YAML, à la requête approuvée.
- **Fenêtre entre le bloc `DO` et `BEGIN`** : le contrôle des caractères de contrôle lit le catalogue juste avant la transaction des requêtes ; un nom changé dans l'intervalle (quelques millisecondes) lui échapperait, mais une ligne coupée par ce nom reste vue par le contrôle du nombre de colonnes et des lignes masquées (§ 5.3), sauf forgerie complète réussie dans cet intervalle (risque (d) : elle suppose déjà un rôle capable de créer des rôles ou des objets sur la base).

### 4. Requêtes R1 à R8 (Sécu ; reprises du head `37fffa4`)

Chacune est préfixée par son étiquette en première colonne et ne lit que `pg_catalog` (le catalogue est lisible par tout rôle connecté ; aucune donnée de table n'est lue, donc ni donnée Google ni donnée personnelle) :

- **R1 extensions** : `pg_extension` — nom, version, schéma ;
- **R2 fonctions d'extension** : `pg_proc` joint à `pg_depend` (`classid = 'pg_proc'::regclass`, `objid = pg_proc.oid`, `deptype = 'e'`, `refclassid = 'pg_extension'::regclass`, `refobjid = pg_extension.oid` ; sans `classid`, un `objid` pourrait être l'oid d'un objet d'un autre catalogue) — extension, `oid::regprocedure`, `prosecdef`, propriétaire, `proacl::text`, **`has_function_privilege('vadrouille_prototype', oid, 'EXECUTE')`** (six colonnes ; mineur 11 du head `2010c68` : un `proacl` nul vaut `EXECUTE` à `PUBLIC` par défaut, et une appartenance de `vadrouille_prototype` à un rôle qui a `EXECUTE` ne se lit pas dans l'ACL ; le verdict de la Sécurité sur « appelable par `vadrouille_prototype` ou par `PUBLIC` » (0056, § 4.1, condition 4) repose sur cette colonne, et sur `proacl` pour `PUBLIC`) ;
- **R3 rôles** : `pg_roles` — nom, `rolsuper`, `rolinherit`, `rolcreaterole`, `rolcreatedb`, `rolcanlogin`, `rolreplication`, `rolbypassrls` ;
- **R4 appartenances** : `pg_auth_members` — rôle, membre, auteur, `admin_option`, `inherit_option`, `set_option` (PostgreSQL 16 ou plus), dont l'appartenance éventuelle de l'identifiant propriétaire à `pg_signal_backend` (0056, § 4.6, point 3) ;
- **R5 droits par table et par colonne** : `pg_class` des schémas `public`, `prototype` et `vadrouille_migrations` — schéma, nom, `relkind`, propriétaire, `relacl::text`, `relrowsecurity`, `relforcerowsecurity` ; `pg_attribute` de ces relations dont `attacl` n'est pas nul — relation, colonne, `attacl::text` ;
- **R6 fonctions** des schémas `public` et `prototype` — `oid::regprocedure`, `prosecdef`, propriétaire, `proacl::text`, `proconfig::text` (`PUBLIC` y apparaît comme `=X/…` ; les `vadrouille_fn_*` comme propriétaires) ;
- **R7 privilèges par défaut** : `pg_default_acl` — rôle, schéma, type d'objet, `defaclacl::text` ;
- **R8 verrou S8** : pour **chaque surcharge existante** de `public.store_prototype_coordinates`, trouvée dans `pg_proc` par nom et schéma : `oid::regprocedure` et `has_function_privilege('vadrouille_prototype', oid, 'EXECUTE')`. La fonction est désignée par son `oid`, jamais par une signature écrite : une signature absente ne lève pas d'erreur, elle n'apparaît pas. La signature à quatre paramètres n'existe qu'après l'application de la migration de remplacement de 0052 § 1.7 (lot 2 de 0056) ; **avant, R8 ne peut pas la viser**, et la condition 4 du § 4.1 de 0056 n'est pas réunie. **Une surcharge absente n'apparaît pas** (mineur 5 du head `2010c68`) : le verdict de la condition 4 **exige la ligne R8 de la signature à quatre paramètres** ; son absence dans un relevé fait après l'application du lot 2 est une **anomalie** (migration non appliquée, fonction supprimée ou renommée hors du workflow), consignée comme telle, sans verdict favorable.

### 5. Sortie publique et motif (Sécu ; outillage : TL)

La sortie standard et d'erreur de `psql` vont dans un fichier de `$RUNNER_TEMP`, jamais affiché ni téléversé (une erreur de connexion commence par `psql:` et peut nommer l'hôte). Seules les lignes de ce fichier qui suivent le motif figé ci-dessous et ont le nombre de colonnes de leur étiquette sont affichées, et seulement si tous les contrôles du § 5.3 passent.

**5.1 Motif et forme exacte d'affectation (bloquant 1).** Le motif contient une apostrophe (`$'@` de la classe) : il ne peut pas être tenu entre apostrophes d'un seul tenant. Il est affecté par **cette ligne exacte**, seule affectation de `motif` dans le bloc `run:`, à écrire telle quelle (le test la compare à la chaîne exacte, § « Tests imposés ») :

```bash
motif='^R[1-8](\|[][A-Za-z0-9_.,:;=/{}"()*+$'"'"'@<>#\ -]{0,500}){1,8}$'
```

Lecture de la ligne : trois mots collés, `'^R[1-8](\|[][A-Za-z0-9_.,:;=/{}"()*+$'` entre apostrophes, `"'"` (une apostrophe entre guillemets), `'@<>#\ -]{0,500}){1,8}$'` entre apostrophes ; aucune expansion n'a lieu (`$'` et `\` restent littéraux dans les deux parties entre apostrophes). La valeur obtenue est :

```text
^R[1-8](\|[][A-Za-z0-9_.,:;=/{}"()*+$'@<>#\ -]{0,500}){1,8}$
```

La forme ANSI-C `$'…'`, qui demanderait d'échapper `\` et `'`, n'est pas retenue (§ 8). Le motif est une expression régulière étendue POSIX, employée **sans guillemets** à droite de `=~` : `[[ $ligne =~ $motif ]]`, sous `LC_ALL: C`. Lecture : l'étiquette `R1` à `R8`, puis de une à huit colonnes (R3, la plus large, en a huit), chacune précédée du séparateur `|` de `-F '|'` et formée de **0 à 500 caractères** d'une **classe fermée qui exclut `|`** : lettres et chiffres ASCII, `_ . , : ; = / { } " ( ) * + $ ' @ < > #`, `[` et `]` (`regprocedure` avec tableau, `text[]`, R2 et R6), `\` (guillemet échappé dans `proconfig::text`), espace et `-`. Une colonne vide (ACL nulle, schéma nul de `pg_default_acl`) est admise. Ni tabulation, ni caractère de contrôle (séquence d'échappement de terminal), ni octet hors ASCII, et une ligne commence toujours par `R` : aucune commande de workflow (`::…`) ni ligne `psql:` ne peut être affichée.

**5.2 Lecture et coût (mineur 3).** Le fichier est lu une fois par `mapfile -t -n 601 lignes < "$sortie"` (redirection vers `mapfile`, pas vers `psql`) ; **plus de 600 lignes : échec**, par un message fixe, sans rien afficher. Puis chaque ligne du tableau est comparée au motif (`for ligne in "${lignes[@]}"`) et rangée dans l'un de deux tableaux (§ 5.3) ; **rien n'est affiché avant la fin de tous les contrôles**, puis les lignes retenues le sont par `printf '%s\n' "${affichees[@]}"`. Relevés de la Sécurité dans le bac à sable (bash 5.2.21, celui d'`ubuntu-24.04`, `LC_ALL=C`), car bash recompile l'expression à chaque `[[ =~ ]]` et la borne répétée huit fois en fixe le coût : borne 2 000 (head `37fffa4`) : 0,43 s par ligne courte, soit environ 90 s pour 209 lignes réalistes ; **borne 500 : 0,036 s par ligne réaliste (7,6 s pour 209 lignes), 0,40 s par ligne de huit colonnes de 500 caractères**, soit au plus 240 s pour 600 lignes de ce pire cas. **Les mesures de la revue du head `2010c68` donnent 0,46 à 0,58 s par ligne de pire cas**, soit 275 à 350 s pour 600 lignes (mineur 7) ; mesure refaite par la Sécurité le 2026-10-14 (même version de bash) : 0,34 s par ligne de pire cas (R3, huit colonnes de 500 caractères) et 0,048 s par ligne R6 réaliste. La règle « pire cas ≤ la moitié du `timeout-minutes` » n'était pas tenue à 10 minutes ; **`timeout-minutes` est porté à 15** (900 s, moitié 450 s ≥ 350 s ; marge d'environ 2,6 sur la mesure la plus lente), le plafond de 600 lignes restant inchangé (un relevé attendu de 150 à 300 lignes garde de la place). Un relevé attendu compte environ 150 à 300 lignes (rôles prédéfinis de PostgreSQL, rôles du projet et de Neon, appartenances, tables, fonctions). **Filtrage unique par `grep -aE` écarté** : avec la même répétition bornée imbriquée, GNU grep 3.11 a mis 16 s sur 6 lignes à la borne 500, et n'a pas terminé en plus de 100 s à la borne 2 000 sur 10 lignes négatives (§ 8). La PR de `db-releve.yml` refait la mesure sur `ubuntu-24.04` et la joint ; si le pire cas dépasse la moitié du `timeout-minutes`, elle abaisse le plafond de lignes, jamais la classe.

**5.3 Échec fermé (mineur 2 du head `37fffa4` ; bloquant 1 et mineurs 4 et 6 du head `2010c68`).** Chaque ligne lue va dans **l'un de deux tableaux, remplis par `+=`** : `affichees` si elle suit le motif **et** a le nombre exact de colonnes de son étiquette, `masquees` si elle ne suit pas le motif. **Nombre exact de colonnes par étiquette** (mineur 4 ; contrôle ajouté **à côté** du motif figé, qui reste celui du § 5.1 : une alternative par étiquette dans le motif multiplierait par plus de cinq le texte que bash recompile à chaque ligne), écrit dans cette forme, sans arithmétique :

```bash
seps=${ligne//[^|]/}
case ${ligne:0:2}:${#seps} in
  R1:3|R2:6|R3:8|R4:6|R5:3|R5:7|R6:5|R7:4|R8:2) affichees+=("$ligne") ;;
  *) echec=colonnes ;;
esac
```

(R5 a deux formes : sept colonnes par table, trois par colonne de table.) Un `|` dans un nom ajoute une colonne : la ligne n'a plus le compte de son étiquette et le relevé échoue. Le job **échoue, sans rien afficher des lignes**, (a) si une ligne qui suit le motif n'a pas le nombre de colonnes de son étiquette ; (b) **si le tableau `masquees` n'est pas exactement, dans cet ordre, (`SET`, `DO`, `BEGIN`)** : `[[ ${#masquees[@]} != 3 || ${masquees[0]} != SET || ${masquees[1]} != DO || ${masquees[2]} != BEGIN ]]` (comparaisons de chaînes ; la seule taille comparée est `${#…}`) — une ligne `R[1-8]|` hors classe ou trop longue ne suit pas le motif, va dans `masquees` et fait échouer le job par cette cause, qui remplace la règle « ligne `R[1-8]|` hors motif » du head `2010c68` ; (c) si le code de sortie de `psql` n'est pas 0 ; (d) au-delà de 600 lignes : un relevé tronqué ou en erreur ne passe jamais pour complet. Une ligne coupée par un saut de ligne dans une valeur (nom de rôle, d'objet, `proconfig`) donne une seconde ligne : si elle ne suit pas le motif, elle s'ajoute à `masquees` (cause (b)) ; si elle le suit, l'une des deux moitiés n'a en général pas le compte de son étiquette (cause (a)) ; une forgerie qui tiendrait les deux comptes (relevée dans le bac à sable : `R3|x|f|f|f|f|f|f|f` puis `R3|faux|f|t|f|f|f|f|f`, issue d'un seul nom de rôle) est arrêtée **avant** les requêtes par le contrôle des caractères de contrôle du bloc `DO` (§ 3, cause (c)). Si tout passe, le job affiche les lignes retenues, puis le **nombre de lignes lues**, **affichées** et **masquées** (`${#lignes[@]}`, `${#affichees[@]}`, `${#masquees[@]}`) et le code de sortie de `psql` ; en cas d'échec, seuls ces compteurs, le code de sortie et la cause (message fixe : « colonnes », « lignes masquées », « psql », « plafond ») sont affichés. `${ligne:0:2}` emploie des bornes constantes, aucune valeur lue n'entre dans une expression arithmétique. **Ce refus est assumé** : un caractère légitime hors de la classe (`%`, `!`, `&`, `~`, `?`, `^`, une lettre accentuée ou tout octet hors ASCII, par exemple dans un nom entre guillemets ou un `proconfig`), une colonne de plus de 500 caractères (ACL longue), plus de huit colonnes, un nombre de colonnes autre que celui de l'étiquette (un `|` dans un nom) ou un caractère de contrôle dans un nom fait échouer le relevé entier, sans rien afficher de la ligne fautive. C'est une perte de disponibilité, jamais une fuite : la classe reste fermée par défaut. La Sécurité analyse alors le run sans en afficher le contenu (elle ne voit que les compteurs et le code de sortie), et la correction est une PR de workflow qui ajuste la requête (par exemple `pg_catalog.quote_ident`, `pg_catalog.left`) ou le motif ; **un changement du motif ou des cas figés amende cette décision** dans la même PR, le test comparant le YAML à ce texte.

**5.4 Lignes masquées attendues.** Sans `-q`, `psql` écrit aussi les messages de commande des trois premiers `-c` : **exactement trois lignes, `SET`, `DO`, `BEGIN`**, dans cet ordre (relevé par la Sécurité le 2026-10-14 avec `psql` 16.15 et un serveur local : avec `-A -t`, les requêtes R1 à R8 n'écrivent ni en-tête ni compte de lignes). Ce sont les seules lignes masquées d'un run normal ; tout autre contenu (message `NOTICE`, `WARNING`, `ERROR`, `psql:`, ligne coupée) fait échouer le job par la cause (b) du § 5.3 : **le contrôle est fait par le job, plus seulement par la relecture humaine** (bloquant 1 du head `2010c68`). La Sécurité vérifie de plus, dans le run consigné, que les compteurs affichés valent bien lues = affichées + 3.

**5.5 Cas figés**, que le test « motif de sortie » vérifie contre la valeur extraite du YAML (§ « Tests imposés »). Les exemples sont des formes, pas un état attendu de la base (les noms propres à Neon, comme `neondb_owner`, sont illustratifs).

Ce masquage confirme aussi publiquement qu'une chaîne affichée contient la valeur d'un secret ; pour le nom de base, déjà prévisible chez Neon, l'effet est jugé négligeable.
