### 2.2 Réponses HTTP

Identiques à 0097 B4-TL-11 point 2, sans exception : `200` `{"received":true}` pour tout événement vérifié et traité (accordé, déjà accordé, ignoré, refusé par un contrôle, session inconnue, identifiant simulé) ; `400` `{"error":"invalid_request"}` (signature absente, fausse ou hors tolérance, en-tête de plus de 512 caractères, type de média autre que `application/json`, corps signé illisible) ; `404` corps vide (fermé) ; `405` avec `Allow: POST` ; `413` ; `500` `{"error":"server_error"}` sur une panne de base seulement. 0081 (B9-TL-12, option B, rappelée par 0097 B4-TL-12) s'applique : la réponse ne dépend pas de la suite.

Lecture de la documentation de Stripe (sources ci-dessous) : toute réponse hors `2xx` est un échec relivré ; en mode test, Stripe relivre **trois fois sur quelques heures** ; en mode réel, **jusqu'à trois jours** avec recul exponentiel ; une redirection `3xx` est un échec (chiffres relevés sur la page lue le 2026-10-28, non revérifiés depuis ; aucune décision n'en dépend ; **B4c relit la page de Stripe sur les relivraisons** avant de s'appuyer sur ces chiffres et note dans sa PR ce qu'elle y lit). Cela répond à la question laissée par B4-TL-12 option A (« durée de relivraison … à vérifier par B4c ») : l'option B retenue par 0081 évite les `500` prolongés ; un `500` ne survient que sur panne de base, et la relivraison est voulue (B4-PO-13). La règle de désactivation d'un point de terminaison n'est pas décrite par les pages lues : elle n'est pas présumée (« Quand revoir »).

### 2.3 Vérification de la signature

Format (documentation, « Verify webhook signatures manually ») : en-tête `Stripe-Signature: t=<secondes>,v1=<hex>[,v1=…][,v0=…]` ; seul le schéma `v1` compte (`v0` est une fausse signature des événements de test, à ignorer contre la rétrogradation) ; `v1` = HMAC-SHA-256, clé = le secret `whsec_…` du point de terminaison, message = `<t>` + `.` + corps brut ; comparaison à temps constant ; plusieurs `v1` pendant la rotation d'un secret (jusqu'à 24 h). C'est le format de 0097 B4-TL-2 point 2.

1. **Corps brut** : `verifierEvenementStripe` reçoit les **octets** lus par `lireCorps` (jamais `request.json()` ni une chaîne réencodée), passés tels quels (`Buffer`) à `constructEvent`. La documentation l'exige (« Stripe requires the raw body of the request »).
2. **Tolérance : 300 s, passée explicitement** (valeur par défaut des bibliothèques, « default tolerance of 5 minutes ») ; jamais `0` (la documentation : « Don't use a tolerance value of `0`. Using a tolerance value of `0` disables the recency check entirely »). La garde contre un horodatage **futur** de 0097 B4-TL-2 point 3 n'est **pas** reprise sur la route Stripe : la vérification de la bibliothèque ne compare que l'âge (lecture de 0097 B4-TL-2 ; T4 épingle ce comportement de 23.0.0, horloge injectée) et un horodatage futur exige le secret ; une garde maison réintroduirait du code maison sur le chemin Stripe, contre le choix de 0097 B4-TL-2 point 4. Écart assumé entre les deux routes, borné par T4.
3. **Rejeu** : la tolérance borne la fenêtre ; à l'intérieur, l'idempotence par identifiant d'événement fait qu'un rejeu n'écrit rien et n'accorde rien de plus (`webhook.ts` l. 81-83 et l. 136-137 ; A1 rejoué). Stripe signe chaque nouvelle livraison avec un nouvel horodatage (documentation), donc une relivraison légitime n'est jamais refusée pour son âge.
4. **Aucune fuite par l'erreur** : l'erreur levée par `constructEvent` porte l'en-tête et le corps reçus. `verifierEvenementStripe` l'attrape **sans la lier ni la journaliser** (`catch {}`), ne la relance pas et rend `false` ; la route répond `400` sans journal (comme le simulé, l. 124). Test T5 (A19 étendu).
5. **Plafond d'en-tête avant tout calcul** : un en-tête `Stripe-Signature` absent ou de plus de 512 caractères (`LONGUEUR_MAX_ENTETE`, `signature.ts` l. 18, réutilisée) donne `400` sans appeler `constructEvent` (espion). Aucun autre analyseur maison de l'en-tête.
6. **Liste d'adresses IP de Stripe** : non retenue en B4c. La documentation la recommande en plus de la signature ; elle demande une règle de pare-feu ou un en-tête d'IP de confiance sur la préversion (réglage de compte Vercel : Samuel) et une liste à tenir à jour. La signature suffit au mode test ; à revoir avant tout mode réel (« Quand revoir »).

## 5. Création de la session Stripe (adaptateur `stripe`, B4c point 2)

Précisions techniques nécessaires aux critères C1, C5 et A15 sur `stripe` :
0. **Point de jonction `PrestatairePaiement`**. Sur `main`, le port rend `Promise<string>` (`paiements.ts` l. 33) et `depart()` construit `redirectUrl` par `cheminSimulation` (l. 127-131). B4c le remplace par :
   - `creerSession(paiement: { readonly id: string; readonly checkoutId: string; readonly tripId: string; readonly amount: number; readonly currency: string; readonly method: PaymentMethod; readonly createdMs: number }, cleIdempotence: string): Promise<ResultatPrestataire<{ readonly sessionId: string; readonly redirectUrl: string }>>` ;
   - `adresseSession(sessionId: string, paiement: { readonly id: string; readonly checkoutId: string; readonly tripId: string }): Promise<ResultatPrestataire<string>>` ;
   - dans `paiement`, `id` est l'`uuid` **interne** (`checkouts.id`) et `checkoutId` l'identifiant **public** ; **`creerCasPaiement` fait la conversion** (`versIdentifiantPublic(ligne.id)`, comme `depart` aujourd'hui, `paiements.ts` l. 128) et passe les deux : le prestataire simulé emploie `checkoutId` pour `cheminSimulation`, le prestataire Stripe emploie `id` pour `metadata.checkoutId` et la clé d'idempotence ; aucun prestataire ne convertit. **Ce qui ne change pas** : `PaiementAEmettre` et `evenementSimule` (`simulated-provider.ts`) restent tels quels ; `emettre` garde l'`uuid` interne dans `checkoutId` (`paiements.ts` l. 254, comparé à `ligne.id` par `webhook.ts` l. 58-59) ; seule la forme du paramètre de `creerSession` change ;
   - `type ResultatPrestataire<T> = { readonly ok: true; readonly value: T } | { readonly ok: false; readonly code: "provider_error"; readonly retryable: boolean }`.
   **C'est le prestataire qui construit `redirectUrl`** : le prestataire simulé rend le chemin de `cheminSimulation` (qui passe de l'appel de `depart` à sa fabrique) ; le prestataire Stripe rend le champ `url` de la session après `adressePrestataireAdmise` (§ 4). `depart(ligne, redirectUrl)` ne fait plus que valider par `CheckoutStartSchema` et reçoit l'adresse ; `cheminSimulation` disparaît de `creerCasPaiement`. `sessionId` est écrit en (c) ci-dessous, `redirectUrl` n'est jamais stocké.
1. **Adaptateur** `src/adapters/stripe-payment.ts` (fabrique `createStripePaymentAdapter(dépendances)`, sur le modèle de `simulated-payment.ts`) ; il ne connaît que l'interface étroite de § 1.2, injectée : un **double** en test (C1, A22), le client réel par `src/server/payment/composition-stripe.ts` (seul appelant de `cleStripe` hors tests), branché comme le simulé par B4b (`src/adapters/simulated-payment-instance.ts` et `src/instrumentation.ts` sur la branche de #836). `getPaymentAdapter()` accepte `stripe` (fin du « non implémenté » de `src/adapters/index.ts` l. 163-164) ; `paymentAvailable()` gagne une branche `stripe` sur le modèle de B4-TL-14 (jamais vraie si `isProductionTarget`, § 3 point 6), amendement de 0020 § 2.3 écrit par B4c ; `getPaymentSimulator()` rend `null` pour `stripe`.
2. **La ligne `checkouts` est validée avant l'appel à Stripe** (B4c point 2) : B4c sépare la transaction de `createCheckout` (`paiements.ts` l. 189-216) en trois temps : (a) transaction d'insertion validée ; (b) appel à Stripe **hors transaction** ; (c) transaction courte `UPDATE checkouts SET stripe_checkout_session_id = $1 WHERE id = $2 AND stripe_checkout_session_id IS NULL` (écrit une seule fois). Si l'`UPDATE` touche 0 ligne (reprise concurrente), la même transaction relit l'identifiant stocké : égal à celui reçu, la suite continue ; différent, `provider_error` (`retryable: false`), rien d'autre écrit. **Tout appel au prestataire, `creerSession` comme `adresseSession`, se fait hors de toute transaction** ; la lecture de `memeDemande` (`paiements.ts` l. 191-198) reste dans sa transaction, qui est validée avant l'appel. Le chemin simulé garde la même forme (pas deux chemins), ses tests restant verts.
3. **Idempotence vers Stripe** : clé d'idempotence `checkout:<uuid interne du paiement>`, pour qu'une reprise après une panne entre (a) et (c) recrée la **même** session. Reprise par le même `requestId` : session absente → appel (b) avec la même clé puis (c), au lieu du `provider_error` actuel (l. 196), **seulement si** la ligne a le statut stocké `pending` **et** que l'horloge injectée (`maintenant()` des dépendances) est à **moins de 120 s** de sa création (`maintenant − createdMs < 120 000`, borne stricte). Sinon : `provider_error` (`retryable: false`), aucun appel au prestataire, rien d'écrit, et l'écran propose un nouveau paiement (F9). Raison : `expires_at` est fixé une fois pour toutes à la création de la ligne + 30 min + 120 s (point 4) ; au-delà de 120 s, il tomberait à moins de 30 min de la création de la session chez Stripe, qui refuserait, et le recalculer changerait les paramètres envoyés sous la même clé (erreur d'idempotence). Si Stripe refuse malgré tout (latence près de la borne), le refus (`StripeInvalidRequestError`, `retryable: false`) mène au même F9. **Aucune session n'est jamais créée pour une ligne `paid`, `declined`, `cancelled` ou lue `expired`** ; session présente → `adresseSession(sessionId, paiement)` hors transaction (lecture de la session pour son `url`, aucune migration), qui rend `provider_error` sauf si la session lue a `metadata.checkoutId` égal à `paiement.id`, le statut `open` et un `url` admis par `adressePrestataireAdmise` ; puis `redirectUrl`. Session expirée, close ou sans `url` : `provider_error` (`retryable: false`), l'écran propose un nouveau paiement (comportement F9 existant).
4. **Paramètres** (C5) : `mode: "payment"` ; un `line_items` en `price_data` (`currency` en minuscules et `unit_amount` = instantané de la ligne, nom du produit constant sans donnée de la personne), `quantity: 1` ; `payment_method_types` = les moyens de l'offre (`src/server/config/offer.ts` l. 21 : `twint`, `card` ; TWINT n'accepte que le CHF, documentation) ; `metadata.checkoutId` = l'`uuid` interne (contrôle `checkout_mismatch`, `webhook.ts` l. 58) ; `client_reference_id` absent ; ni `customer`, ni `customer_email` ; `success_url` et `cancel_url` construits depuis `APP_URL` par le module d'adresses (B4c point 3, C2) ; **`expires_at` = création de la ligne + 30 min + 120 s**. Raison de la marge : la documentation fixe le minimum à 30 min **après la création de la session chez Stripe** (« anywhere from 30 minutes to 24 hours after Checkout Session creation »), qui suit la création de la ligne ; sans marge, l'appel serait refusé. La durée de vie affichée reste 30 min (B4-PO-4 inchangée). Conséquence à connaître : un paiement encaissé dans les 120 s de marge passe par A14 (`paid_after_failure`) et **accorde le droit alors que l'écran affiche déjà « expiré »** ; la personne qui recharge voit le voyage débloqué. **Sous réserve de l'accord du Product Owner** (« Questions nouvelles », 3) ; sans accord, B4c revient au Tech Lead avant de coder ce paramètre (§ 10).
5. Aucune donnée de la personne n'est lue de l'événement (déjà la règle d’`evenement.ts` l. 8-9) ni journalisée.
