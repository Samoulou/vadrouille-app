## Contexte
Q294 (Samuel, 2026-10-13 22:01 CEST, « Bouton GitHub ») : les migrations passent par un workflow GitHub déclenché à la main par le studio. #283 a cherché à rendre ce workflow sûr par des **contrôles ajoutés à l'exécuteur** : liste des commandes bash admises, interdits arithmétiques, enveloppe `DO … EXECUTE`, ordre insertion / déclencheurs différés / contrôles, puis, pour tenir le verrou S8 sur la base réelle, un relevé du catalogue après chaque migration (droits de `vadrouille_prototype`, rôles « capables », extensions, déclencheurs différés, empreintes des fonctions). Quatre revues consolidées ont chacune trouvé de nouveaux détours (vue sans `security_invoker`, `ALTER EXTENSION … ADD FUNCTION`, fonction en droits de l'invoqueur appelée par une fonction `SECURITY DEFINER`, appartenances transitives, `pg_default_acl`, `pg_db_role_setting`, évaluation arithmétique de `[[ -gt ]]`), puis un visa Sécurité qui ne liait pas le commit appliqué.

**Leçon (Sécu, TL).** La classe « ce qu'un SQL arbitraire peut faire sous `vadrouille_migrator` » est ouverte : la détecter après coup donne un texte sans fin et une fausse assurance. Cette décision inverse l'approche : **refus par défaut** ; seul passe un SQL dont l'empreinte a été **approuvée par Samuel** dans un fichier que 0035 protège déjà. L'exécuteur ne juge plus le SQL ; il vérifie une égalité d'empreintes.

## Décision

### 1. Principe (Sécu) — S9 révisée
**S9 — Aucune migration n'atteint la base réelle sans que son nom et son empreinte SHA-256 figurent dans la liste d'approbation écrite dans `.github/workflows/db-migrate.yml`, que seul Samuel approuve (`owner-approved`, 0035). Le workflow n'exécute aucun fichier du dépôt et n'envoie à la base que des textes dont l'empreinte est dans la liste. Tout le reste est refusé.**

Conséquences directes :
1. **Lancer est sans risque propre** : un lancement n'applique que des migrations déjà approuvées ; le moment du clic n'a plus à être lié à un visa (bloquant 1 du head `10406b4` résolu par construction).
2. **Le verrou S8 sur la base réelle est la liste** : aucune migration qui lève S8, directement ou par un détour, n'est appliquée sans que Samuel ait approuvé son empreinte (§ 3). Les détours de #283 deviennent des motifs de refus du verdict Sécurité qui accompagne l'approbation, pas des contrôles de l'exécuteur (bloquant 2 du head `10406b4`).
3. **Le déverrouillage est l'approbation d'une migration d'une instruction** (§ 4) : ni constante dédiée, ni exception dans l'exécuteur.

### 2. Workflow `db-migrate` (exigences : Sécu ; architecture et outillage : TL)
1. **Fichier** `.github/workflows/db-migrate.yml`. **Déclencheur** : `workflow_dispatch` seul, avec **un seul `inputs`**, `sha_attendu` (obligatoire, chaîne). Aucun autre déclencheur.
2. **Branche** : `if: github.ref == 'refs/heads/main'` sur le job, **et** environnement `db-migrate` dont la règle de déploiement n'admet que la branche `main`. C'est l'environnement qui ferme les secrets : un lancement depuis une autre branche exécute le YAML de cette branche, mais GitHub lui refuse l'environnement.
3. **Commit lancé** : l'étape refuse, avant toute connexion, si `sha_attendu` ne suit pas `^[0-9a-f]{40}$` ou diffère de `$GITHUB_SHA` (comparaison `[[ "$sha_attendu" == "$GITHUB_SHA" ]]`). L'entrée passe par `env:` (`SHA_ATTENDU: ${{ inputs.sha_attendu }}`) ; **aucune expression `${{ … }}` d'entrée ni de contexte modifiable dans un bloc `run:`** (injection de script). Le commit consigné est ainsi celui qui a tourné.
4. **Liste d'approbation** : une constante `MIGRATIONS_APPROUVEES`, écrite en clair dans le bloc `run:`, une ligne `<tag> <sha256>` par migration, **dans l'ordre du journal, en ajout seulement**. C'est **la seule source** des noms de migration : le workflow **ne lit pas** `db/migrations/meta/_journal.json`. Chaque ligne est vérifiée (`^[0-9]{4}_[a-z0-9_]{1,60} [0-9a-f]{64}$`) ; une ligne hors forme fait échouer le job.
5. **Code exécuté** :
   - `actions/checkout` épinglé par commit (celui de `ci.yml`), `ref: ${{ github.sha }}`, `persist-credentials: false`, `fetch-depth: 1`, sans sous-module ni LFS ; **aucune autre action** ;
   - aucune commande qui exécute ou charge un fichier du dépôt (`pnpm`, `npm`, `npx`, `node`, `corepack`, `tsx`, `make`, `source`, `.`, `bash <fichier>`, `psql -f`, entrée redirigée vers `psql`) ; commandes externes admises : `sha256sum`, `stat`, `realpath`, `psql -X` ; commandes internes de bash usuelles, sans `eval`, `exec`, `trap`, `export`, `declare`, `let`, `(( ))`, `$(( ))` ;
   - **aucune valeur venue du dépôt n'entre dans une commande avant que son empreinte soit vérifiée** : le texte d'une migration est lu, haché, comparé à la liste, puis seulement envoyé ; une comparaison numérique ne porte que sur `${#…}` ou sur une sortie de `stat` vérifiée auparavant par `^(0|[1-9][0-9]{0,8})$`, sans réaffectation entre la vérification et la comparaison. Comme le journal n'est pas lu, aucune valeur modifiable par une PR ordinaire n'atteint bash avant la vérification d'empreinte (le relevé `a[$(touch …)]` du head `753922b` n'a plus d'entrée).
6. **Une étape, dans cet ordre** (TL : une seule étape suffit, puisque les contrôles n'interprètent aucune donnée non approuvée ; ils précèdent toute connexion). `env:` de l'étape : `SHA_ATTENDU`, `LC_ALL: C`, `PGHOST`, `PGDATABASE`, `PGPASSWORD` (secrets de l'environnement `db-migrate`, noms proposés `MIGRATOR_PGHOST`, `MIGRATOR_PGDATABASE`, `MIGRATOR_PGPASSWORD`), `PGUSER: vadrouille_migrator`, `PGSSLMODE: verify-full`, `PGSSLROOTCERT: system` ; aucune autre variable `PG*`, ni `DATABASE_URL`, ni `VADROUILLE_DATABASE_URL*`.
   1. **Contrôles, sans connexion** : point 3 ; `psql --version` de version majeure 16 ou plus (`sslrootcert=system`, Q388) ; `PGHOST` suit `^[a-z0-9.-]{1,253}$` et `PGDATABASE` `^[a-z0-9_]{1,63}$` ; pour chaque ligne de la liste : le chemin résolu par `realpath -e` est exactement `$GITHUB_WORKSPACE/db/migrations/<tag>.sql` (aucun lien symbolique), fichier ordinaire, non vide, de 100 Kio au plus (limite d'un argument sous Linux : 128 Kio) ; texte lu par `IFS= read -r -d '' texte < "$f"` écrit comme condition de `if` (un octet NUL fait échouer) ; `${#texte}` égal à la taille donnée par `stat` ; **empreinte du texte lu** (`printf '%s' "$texte" | sha256sum`) **égale à celle de la liste** ; premier caractère différent de `\`. Tout écart : échec, aucune connexion, rien n'est appliqué, même pour les lignes précédentes.
   2. **Connexion et rôle** : première requête (`SET search_path = pg_catalog, pg_temp` puis bloc `DO`) : `session_user` et `current_user` valent `vadrouille_migrator`, ni `rolsuper` ni `rolbypassrls`, `ssl` vrai dans `pg_catalog.pg_stat_ssl` pour son processus ; sinon exception.
   3. **Journal** : `CREATE TABLE IF NOT EXISTS vadrouille_migrations.applied …` identique à `db/migrate.ts`, puis lecture des `(tag, sha256)` en `psql -X -A -t -F '|'` ; chaque ligne doit suivre `^([0-9]{4}_[a-z0-9_]{1,60})\|([0-9a-f]{64})$`, sinon échec.
   4. **Application, dans l'ordre de la liste** : déjà appliquée avec la même empreinte, ignorée ; avec une autre, échec (« écrire une nouvelle migration ») ; sinon **une session `psql -X -v ON_ERROR_STOP=1 -v VERBOSITY=sqlstate`** formée de `-c` successifs, **dans l'ordre de `db/migrate.ts`** : `BEGIN` ; verrou consultatif `pg_catalog.pg_advisory_xact_lock(pg_catalog.hashtext('vadrouille_migrations'))` ; nouvelle vérification que le `tag` n'est pas appliqué ; **le texte de la migration en un seul `-c`** (un `-c` n'interprète aucune méta-commande de `psql` mêlée à du SQL ; le premier caractère n'est pas `\`) ; contrôle `current_user = 'vadrouille_migrator'` ; insertion `(tag, sha256)` dans `vadrouille_migrations.applied` ; `COMMIT`. Une erreur arrête `psql` avant le `COMMIT` et la déconnexion annule tout.
   5. **Sortie** : la sortie standard et d'erreur de chaque `psql` vont dans un fichier de `$RUNNER_TEMP`, jamais affiché ni téléversé (une erreur de connexion nomme l'hôte) ; le job n'affiche que les noms appliqués et ignorés, le nombre de lignes de la liste, et en cas d'échec le `tag`, le code de sortie et le seul SQLSTATE, extrait par `while IFS= read -r ligne; do if [[ $ligne =~ ^(ERROR|FATAL):\ +([0-9A-Z]{5})$ ]]; then …; fi; done`. Ni `set -x`, ni affichage de l'environnement.
7. **(TL, Q388)** `permissions: {}` au niveau du workflow ; `contents: read` au niveau du job, pour `actions/checkout` (lecture d'un dépôt public : aucune exposition ajoutée). `runs-on: ubuntu-24.04`, `timeout-minutes: 10`, `concurrency: { group: db-migrate, cancel-in-progress: false }`.
8. **`db/migrate.ts` ne parle qu'à une base locale** : la PR du workflow le modifie pour refuser tout hôte autre que `localhost`, `127.0.0.1` ou `::1`, après analyse de la chaîne par `pg-connection-string` (hôte de l'URL, `?host=`, plusieurs hôtes, socket, forme `clé=valeur`, hôte absent avec `PGHOST`). Ce refus ferme l'autre chemin vers la base réelle (`pnpm db:migrate`, qui exécuterait le code du dépôt avec le secret). La même PR met à jour `db/README.md` (§ 2, étape 7 : « Application à la base Neon : par `db-migrate.yml`, lancé à la main sur `main` (Q294 ; décision 0056), qui n'applique que les migrations approuvées ; jamais depuis l'application, la construction Vercel ni `db/migrate.ts` » ; § 3, « Ce que le studio ne fait pas » : « il n'applique de migration que par ce workflow »).
9. **Qui lance** : le rôle que le CEO désigne (proposition : data), avec `sha_attendu` = tête de `main` relevée juste avant. Pas de visa par lancement (l'approbation est par migration, § 3). Après chaque lancement, il consigne dans le ticket ou la PR : conclusion du run, commit, migrations appliquées et ignorées, sans valeur secrète.
10. **Environnement et secrets** : créés et posés **par Samuel**, sauf s'il étend Q321 (alors par le studio selon S5 de 0046) — Q387, inchangée. Le mot de passe est celui de `vadrouille_migrator`, jamais celui de l'identifiant propriétaire de l'intégration Neon. **Aucun agent ne modifie l'environnement `db-migrate`, sa règle de branche ni ses secrets** après leur création. Relevé (noms seulement : règle de branche, secrets de l'environnement et du dépôt) **par Samuel à la création et après chaque changement qu'il fait**, le mandataire des sessions d'agent refusant ces chemins (Q394) ; il n'est plus exigé avant chaque lancement : un élargissement de la règle exposerait les secrets à toute heure, indépendamment des lancements, et un relevé par lancement ne le fermerait pas.

### 3. Approbation d'une migration (Sécu ; procédure)
1. **PR d'approbation** : une PR de workflow qui **ajoute** à `MIGRATIONS_APPROUVEES` les lignes de migrations déjà sur `main` ou ajoutées par la même PR. Elle attend `owner-approved`, posé par Samuel (0035) ; tout changement ultérieur de la liste retire le libellé. Rien d'autre n'y change le comportement du workflow.
2. **Description** : pour chaque migration, le `tag`, l'empreinte, le lien vers son diff, la CI verte sur le head, et le **verdict Sécurité selon la grille fermée** ci-dessous. Le CEO la signale dans `#studio` (0035) ; « Nouvelles questions » : « Samuel : owner-approved attendu (décision 0035) ».
3. **Grille du verdict, refus par défaut.** Le verdict est « accordé » seulement si :
   - **G1** — la migration ne donne à `vadrouille_prototype`, ni directement, ni par `PUBLIC`, une appartenance, des privilèges par défaut, ni par du code exécuté sous un autre rôle (fonction `SECURITY DEFINER`, vue sans `security_invoker`, déclencheur, règle, politique, défaut, extension), **aucun droit hors de la liste fermée de 0046 (D15 point 6)** ; seule exception : la migration de déverrouillage du § 4 ;
   - **G2** — elle ne contient ni contrôle de transaction (`COMMIT`, `ROLLBACK`, `BEGIN`, `SAVEPOINT`, `PREPARE TRANSACTION`…), ni objet du schéma `vadrouille_migrations`, ni `ALTER ROLE` ou `ALTER DATABASE … SET`, ni `CREATE EXTENSION`, ni appartenance à un rôle `vadrouille_fn_*` qui survive à la migration (modèle de `0001_securite.sql` : accordée, utilisée, révoquée `GRANTED BY vadrouille_migrator`) ;
   - **G3** — le verdict **nomme** chaque objet de code créé ou remplacé qui s'exécute sous un rôle capable d'écrire `place_coordinates` ou d'accorder `EXECUTE` sur `store_prototype_coordinates` (`vadrouille_fn_coords`, `vadrouille_owner`, `vadrouille_migrator`, et tout rôle qui en est membre) : fonction, déclencheur, règle, défaut, politique, vue ; et dit pourquoi aucun ne peut lever S8, maintenant ou plus tard.

   Un « non » à G1 ou G2 donne « changements demandés ». L'**annexe A** liste les détours relevés à #283 comme aide à la lecture ; elle n'est ni exhaustive ni mécanique, et la Sécurité la tient à jour par une PR de décision.
4. **Filets mécaniques (TL)**, sur chaque PR, avant toute approbation : `ci: liste approuvée = préfixe du journal` (chaque ligne de `MIGRATIONS_APPROUVEES` a un `tag` du journal, dans le même ordre, et son empreinte est celle du fichier) ; tests de base existants ou imposés par 0052 (`base: vadrouille_prototype ne peut écrire aucune coordonnée (verrou S8)`, bouclant sur toutes les surcharges, `base: droits de vadrouille_prototype en liste fermée (D15 point 6)`, `migrations: aucune appartenance résiduelle à vadrouille_fn_coords`). Ce sont des filets : la barrière est l'approbation.
5. **Revue Sécurité des chemins `db/`** : convention des consignes (`.claude/agents/securite.md`), sans exigence mécanique avant la fusion automatique (`techlead-gate.yml` ne cite pas `db/`). Elle n'est pas la barrière : une migration fusionnée sans elle n'est pas approuvée, donc pas appliquée.

### 5. Alternatives écartées (Sécu, TL)
- **Contrôles de catalogue dans l'exécuteur** (S11 du head `753922b`) : classe ouverte, nouveaux détours à chaque revue, fausse assurance ; remplacés par la grille du § 3, lue par un humain avant approbation.

- **Enveloppe `DO … EXECUTE` et contrôles après la migration** : ils protégeaient des contrôles de fin qui n'existent plus ; l'exécuteur suit l'ordre de `db/migrate.ts`, ce qui garde un seul comportement à tester.
