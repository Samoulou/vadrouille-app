## Contexte
Q294 (Samuel, 2026-10-13 22:01 CEST, « Bouton GitHub ») : les migrations passent par un workflow GitHub déclenché à la main par le studio. #283 a cherché à rendre ce workflow sûr par des **contrôles ajoutés à l'exécuteur** : liste des commandes bash admises, interdits arithmétiques, enveloppe `DO … EXECUTE`, ordre insertion / déclencheurs différés / contrôles, puis, pour tenir le verrou S8 sur la base réelle, un relevé du catalogue après chaque migration (droits de `vadrouille_prototype`, rôles « capables », extensions, déclencheurs différés, empreintes des fonctions). Quatre revues consolidées ont chacune trouvé de nouveaux détours (vue sans `security_invoker`, `ALTER EXTENSION … ADD FUNCTION`, fonction en droits de l'invoqueur appelée par une fonction `SECURITY DEFINER`, appartenances transitives, `pg_default_acl`, `pg_db_role_setting`, évaluation arithmétique de `[[ -gt ]]`), puis un visa Sécurité qui ne liait pas le commit appliqué.

**Leçon (Sécu, TL).** La classe « ce qu'un SQL arbitraire peut faire sous `vadrouille_migrator` » est ouverte : la détecter après coup donne un texte sans fin et une fausse assurance. Cette décision inverse l'approche : **refus par défaut** ; seul passe un SQL dont l'empreinte a été **approuvée par Samuel** dans un fichier que 0035 protège déjà. L'exécuteur ne juge plus le SQL ; il vérifie une égalité d'empreintes.

## Décision

### 1. Principe (Sécu) — S9 révisée
**S9 — Aucune migration n'atteint la base réelle sans que son nom et son empreinte SHA-256 figurent dans la liste d'approbation écrite dans `.github/workflows/db-migrate.yml`, que seul Samuel approuve (`owner-approved`, 0035). Le workflow n'exécute aucun fichier du dépôt et n'envoie à la base que des textes dont l'empreinte est dans la liste. Tout le reste est refusé.**

Conséquences directes :
1. **Lancer est sans risque propre** : un lancement n'applique que des migrations déjà approuvées ; le moment du clic n'a plus à être lié à un visa (bloquant 1 du head `10406b4` résolu par construction).
2. **Le verrou S8 sur la base réelle est la liste** : aucune migration qui lève S8, directement ou par un détour, n'est appliquée sans que Samuel ait approuvé son empreinte (§ 3). Les détours de #283 deviennent des motifs de refus du verdict Sécurité qui accompagne l'approbation, pas des contrôles de l'exécuteur (bloquant 2 du head `10406b4`).
3. **Le déverrouillage est l'approbation d'une migration d'une instruction** (§ 4) : ni constante dédiée, ni exception dans l'exécuteur.

### 2. Workflow `db-migrate` (exigences : Sécu ; architecture et outillage : TL)
1. **Fichier** `.github/workflows/db-migrate.yml`. **Déclencheur** : `workflow_dispatch` seul, avec **un seul `inputs`**, `sha_attendu` (obligatoire, chaîne). Aucun autre déclencheur.
2. **Branche** : `if: github.ref == 'refs/heads/main'` sur le job, **et** environnement `db-migrate` dont la règle de déploiement n'admet que la branche `main`. C'est l'environnement qui ferme les secrets : un lancement depuis une autre branche exécute le YAML de cette branche, mais GitHub lui refuse l'environnement.
3. **Commit lancé** : l'étape refuse, avant toute connexion, si `sha_attendu` ne suit pas `^[0-9a-f]{40}$` ou diffère de `$GITHUB_SHA` (comparaison `[[ "$sha_attendu" == "$GITHUB_SHA" ]]`). L'entrée passe par `env:` (`SHA_ATTENDU: ${{ inputs.sha_attendu }}`) ; **aucune expression `${{ … }}` d'entrée ni de contexte modifiable dans un bloc `run:`** (injection de script). Le commit consigné est ainsi celui qui a tourné.
4. **Liste d'approbation** : une constante `MIGRATIONS_APPROUVEES`, écrite en clair dans le bloc `run:`, une ligne `<tag> <sha256>` par migration, **dans l'ordre du journal, en ajout seulement** (vérifié mécaniquement par le test `ci: liste approuvée en ajout seulement` du § 3.4, contre le commit de base de la PR). C'est **la seule source** des noms de migration : le workflow **ne lit pas** `db/migrations/meta/_journal.json`. Chaque ligne est vérifiée (`^[0-9]{4}_[a-z0-9_]{1,60} [0-9a-f]{64}$`) ; une ligne hors forme fait échouer le job.
5. **Code exécuté** :
   - `actions/checkout` épinglé par commit (celui de `ci.yml`), `ref: ${{ github.sha }}`, `persist-credentials: false`, `fetch-depth: 1`, sans sous-module ni LFS ; **aucune autre action** ;
   - aucune commande qui exécute ou charge un fichier du dépôt (`pnpm`, `npm`, `npx`, `node`, `corepack`, `tsx`, `make`, `source`, `.`, `bash <fichier>`, `psql -f`, entrée redirigée vers `psql`) ; commandes externes admises : `sha256sum`, `stat`, `realpath`, `psql -X` ; commandes internes de bash usuelles, sans `eval`, `exec`, `trap`, `export`, `declare`, `let`, `(( ))`, `$(( ))` ;
   - **aucune valeur venue du dépôt n'entre dans une commande avant que son empreinte soit vérifiée** : le texte d'une migration est lu, haché, comparé à la liste, puis seulement envoyé ; une comparaison numérique ne porte que sur `${#…}` ou sur une sortie de `stat` vérifiée auparavant par `^(0|[1-9][0-9]{0,8})$`, sans réaffectation entre la vérification et la comparaison. Comme le journal n'est pas lu, aucune valeur modifiable par une PR ordinaire n'atteint bash avant la vérification d'empreinte (le relevé `a[$(touch …)]` du head `753922b` n'a plus d'entrée).
6. **Une étape, dans cet ordre** (TL : une seule étape suffit, puisque les contrôles n'interprètent aucune donnée non approuvée ; ils précèdent toute connexion). `env:` de l'étape : `SHA_ATTENDU`, `LC_ALL: C`, `PGHOST`, `PGDATABASE`, `PGPASSWORD` (secrets de l'environnement `db-migrate`, noms proposés `MIGRATOR_PGHOST`, `MIGRATOR_PGDATABASE`, `MIGRATOR_PGPASSWORD`), `PGUSER: vadrouille_migrator`, `PGSSLMODE: verify-full`, `PGSSLROOTCERT: system` ; aucune autre variable `PG*`, ni `DATABASE_URL`, ni `VADROUILLE_DATABASE_URL*`.
   1. **Contrôles, sans connexion** : point 3 ; `psql --version` de version majeure 16 ou plus (`sslrootcert=system`, Q388) ; `PGHOST` suit `^[a-z0-9.-]{1,253}$` et `PGDATABASE` `^[a-z0-9_]{1,63}$` ; pour chaque ligne de la liste : le chemin résolu par `realpath -e` est exactement `$GITHUB_WORKSPACE/db/migrations/<tag>.sql` (aucun lien symbolique), fichier ordinaire, non vide, de 100 Kio au plus (limite d'un argument sous Linux : 128 Kio) ; **une seule lecture du fichier par migration**, dans cette forme exacte : `if IFS= read -r -d '' texte < "$f"; then` échec (« octet NUL ») `; fi` — `read -r -d ''` ne rend 0 que s'il a trouvé un octet NUL ; à la fin du fichier sans NUL il rend 1 et `texte` contient tout le fichier ; `${#texte}` égal à la taille donnée par `stat` (un texte tronqué échoue) ; **empreinte de cette même variable** (`printf '%s' "$texte" | sha256sum`) **égale à celle de la liste** ; premier caractère différent de `\` ; le texte ne contient pas la chaîne `vadrouille_migrate.` (`[[ $texte == *vadrouille_migrate.* ]]` : échec ; filet de G2, le repère des étapes 3 et 6 de l'application ne doit pas pouvoir être posé par la migration ; une construction dynamique de ce nom reste un motif de refus de G2, que ce filet ne voit pas). Le fichier est en **UTF-8 valide, sans BOM** (§ 3.4) : `db/migrate.ts` hache le texte décodé (`readFileSync(…, "utf8")`), le workflow les octets ; les deux empreintes ne coïncident que pour un UTF-8 valide. Le texte vérifié est gardé dans une variable par migration (tableau indexé par la position dans la liste, rempli à cette étape seulement) ; **aucune relecture du disque ensuite** : ni `cat`, ni `$(< …)`, ni seconde redirection depuis `$f`. Tout écart : échec, aucune connexion, rien n'est appliqué, même pour les lignes précédentes.
   2. **Connexion et rôle** : première session `psql`, distincte de celles des migrations (`SET search_path = pg_catalog, pg_temp` puis bloc `DO` ; ce `SET` meurt avec elle) : `session_user` et `current_user` valent `vadrouille_migrator`, ni `rolsuper` ni `rolbypassrls`, `ssl` vrai dans `pg_catalog.pg_stat_ssl` pour son processus ; sinon exception.
   3. **Journal** : `CREATE TABLE IF NOT EXISTS vadrouille_migrations.applied …` identique à `db/migrate.ts`, puis lecture des `(tag, sha256)` en `psql -X -A -t -F '|'` ; chaque ligne doit suivre `^([0-9]{4}_[a-z0-9_]{1,60})\|([0-9a-f]{64})$`, sinon échec.
   4. **Application, dans l'ordre de la liste** : déjà appliquée avec la même empreinte, ignorée ; avec une autre, échec (« écrire une nouvelle migration ») ; sinon **une session `psql -X -v ON_ERROR_STOP=1 -v VERBOSITY=sqlstate`** formée de `-c` successifs, **dans l'ordre de `db/migrate.ts`** :
      1. `SET lock_timeout = '10s'; SET statement_timeout = '5min'` (une instruction qui attend un verrou échoue au lieu de bloquer l'application ; 5 minutes **par instruction**, ni par migration ni par lot : la durée totale d'un lancement n'est bornée que par le `timeout-minutes` du job, § 2.7, et sa coupure suit la conduite du lot partiel ci-dessous) ;
      2. `BEGIN` ;
      3. **sans aucun `SET`** : verrou consultatif `SELECT pg_catalog.pg_advisory_xact_lock(pg_catalog.hashtext('vadrouille_migrations'))` ; repère de transaction `SELECT pg_catalog.set_config('vadrouille_migrate.txid', pg_catalog.txid_current()::text, true)`. **Aucun `search_path` n'est posé avant le texte** : la migration s'exécute sous le `search_path` par défaut de la session, comme dans `db/migrate.ts` (lignes 85 à 111, qui n'en posent pas) ; `0000_socle.sql` et `0003_prototype.sql` créent des objets non qualifiés qui, sous `pg_catalog, pg_temp`, échoueraient ou atterriraient hors de `public`. Les étapes 3 et 4 tiennent sans `SET` : toute fonction y est qualifiée par `pg_catalog.`, toute table par son schéma, et `pg_catalog` est parcouru en premier tant qu'il n'est pas nommé dans le `search_path` ; le `search_path` par défaut ne peut être changé que par `ALTER ROLE` ou `ALTER DATABASE … SET`, que G2 refuse ;
      4. **contrôle, en bloc `DO` qui lève une exception** : le `tag` n'est pas dans `vadrouille_migrations.applied` (un `-c SELECT` ne ferait pas échouer `psql`) ; objets et fonctions qualifiés, sans `SET` ;
      5. **le texte de la migration en un seul `-c`**, la variable vérifiée à l'étape 1, telle quelle (un `-c` est envoyé au serveur sans interprétation des méta-commandes ni des variables de `psql` ; le premier caractère n'est pas `\`) ;
      6. `SET LOCAL search_path = pg_catalog, pg_temp` (premier `search_path` posé par l'exécuteur dans la transaction, **après** le texte : il ne vaut que pour le contrôle et l'insertion qui suivent), puis **contrôle, en bloc `DO` qui lève une exception** : `session_user` et `current_user` valent `vadrouille_migrator` (un `SET ROLE` ou `SET SESSION AUTHORIZATION` non local est vu) ; `pg_catalog.current_setting('session_replication_role')` vaut `origin` ; `pg_catalog.current_setting('vadrouille_migrate.txid', true)` égale `pg_catalog.txid_current()::text` (un `COMMIT` ou un `ROLLBACK` dans le texte efface le repère local : échec ; ce qui précède un `COMMIT` reste validé sans être journalisé : incident traité comme un lot partiel, G2 devant l'avoir refusé) ;
      7. insertion `(tag, sha256)` par `INSERT INTO vadrouille_migrations.applied …`, toutes les fonctions appelées qualifiées par `pg_catalog.` ;
      8. `COMMIT`.

      Une erreur arrête `psql` avant le `COMMIT` et la déconnexion annule la migration en cours. Un `SET` non local laissé par le texte (`search_path`, paramètre de session) meurt avec la session, ouverte pour cette seule migration. **Lot partiel** : chaque migration a sa session et sa transaction ; si la troisième d'un lot échoue, les deux premières restent appliquées et journalisées, la troisième ne laisse rien, les suivantes ne sont pas tentées. Conduite : le lanceur consigne le run (§ 2.9) et prévient la Sécurité et le data ; aucun nouveau lancement avant l'analyse ; la correction est une PR de workflow qui modifie le fichier en échec et **remplace son empreinte dans la liste**, seule exception à l'ajout seulement (§ 3.4), avec un nouveau verdict ; un lancement ultérieur reprend à cette migration. Un échec par délai (`lock_timeout`, `statement_timeout`) suit la même conduite, sans modification du fichier si l'analyse conclut à une attente passagère. **Job arrêté** par son `timeout-minutes` ou annulé : le runner coupe la connexion, le serveur annule la migration en cours, les précédentes restent journalisées ; même conduite. Le verdict G6 estime la durée d'un lot ; un lot dont l'estimation dépasse la moitié du délai du job est découpé en plusieurs lancements.
   5. **Sortie** : la sortie standard et d'erreur de chaque `psql` vont dans un fichier de `$RUNNER_TEMP`, jamais affiché ni téléversé (une erreur de connexion nomme l'hôte) ; le job n'affiche que les noms appliqués et ignorés, le nombre de lignes de la liste, et en cas d'échec le `tag`, le code de sortie et le seul SQLSTATE, extrait par `while IFS= read -r ligne; do if [[ $ligne =~ ^(ERROR|FATAL):\ +([0-9A-Z]{5})$ ]]; then …; fi; done`. Ni `set -x`, ni affichage de l'environnement.

   - **G1 (verrou S8 et `vadrouille_prototype`)** — la migration ne donne à `vadrouille_prototype` **aucun droit hors de la liste fermée de 0046 (D15 point 6)**, par aucun des chemins suivants, chacun examiné :

     3. appartenance de `vadrouille_prototype` à un autre rôle ;

     5. code exécuté sous un autre rôle et appelable par lui : fonction `SECURITY DEFINER`, vue sans `security_invoker`, déclencheur, règle, politique, valeur par défaut, fonction d'extension ;

   - **G4 (RLS et droits, 0007)** — aucune table n'est soustraite à la RLS : ni `DISABLE ROW LEVEL SECURITY`, ni `NO FORCE ROW LEVEL SECURITY` ; toute nouvelle table a `ENABLE` et `FORCE ROW LEVEL SECURITY` ; aucune politique `USING (true)` ou `WITH CHECK (true)` hors de la liste fermée de 0007 (amendée par 0046) ; aucun `BYPASSRLS` (déjà refusé par G2 au titre d'`ALTER ROLE`) ; aucun droit nouveau à `PUBLIC` ; les droits de `vadrouille_app`, `vadrouille_auth`, `vadrouille_prototype_purge` et des rôles `vadrouille_fn_*` ne s'étendent qu'à ce que la spécification de la tâche nomme ; chaque fonction `SECURITY DEFINER` créée ou remplacée est durcie comme l'exige `fonctions: SECURITY DEFINER durcies` (0007 : `SET search_path = pg_catalog, pg_temp`, objets qualifiés, propriétaire `vadrouille_fn_*` attendu, `EXECUTE` retiré à `PUBLIC`, accordé aux seuls rôles prévus) ;

## Annexe A — Détours relevés à #283 (aide à la lecture du verdict, non exhaustive)
Pour chacun, la question G1 ou G3 est : « ce code ou ce droit permet-il, maintenant ou plus tard, d'exécuter `store_prototype_coordinates` ou d'écrire `place_coordinates` pour `vadrouille_prototype` ? »
- `GRANT` direct, à `PUBLIC`, sur colonnes (`INSERT (…)`), `ON ALL FUNCTIONS IN SCHEMA`, `TRUNCATE`, `TRIGGER` ; changement de propriétaire ; `ALTER DEFAULT PRIVILEGES` (`pg_default_acl`).
- Appartenance à `vadrouille_fn_coords` ou à un rôle capable accordée à un autre rôle (y compris `vadrouille_app`, `vadrouille_owner`, chaîne transitive, `INHERIT` seul).
- Fonction `SECURITY DEFINER` d'un rôle capable, nouvelle ou remplacée (`CREATE OR REPLACE`, `BEGIN ATOMIC`, langage, `proconfig`, valeurs par défaut des arguments) ; fonction en droits de l'invoqueur appelée par une telle fonction (politique, déclencheur, défaut, contrainte, fonction auxiliaire).
- Vue ou vue matérialisée sans `security_invoker` qui appelle une fonction `SECURITY DEFINER` ; règle (`pg_rewrite`) ; politique forcée.
- Déclencheur immédiat ou différé (`CONSTRAINT TRIGGER … DEFERRABLE`), y compris sur `vadrouille_migrations.applied`.
- Extension (`CREATE EXTENSION`, `ALTER EXTENSION … ADD FUNCTION`) ; `pg_cron`, `dblink`, `pg_background`.
- `ALTER ROLE` / `ALTER DATABASE … SET` (`pg_db_role_setting` : `search_path`, `default_transaction_read_only`, `statement_timeout`).
- Héritage ou partition attachée à `place_coordinates`.
- Contrôle de transaction au niveau SQL du script (`BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT`, `PREPARE TRANSACTION`, `COMMIT AND CHAIN`), ou `COMMIT` dans un corps plpgsql ou une procédure (G2) ; les `BEGIN` et `END` d'un corps plpgsql ou d'un `BEGIN ATOMIC` sont admis.
