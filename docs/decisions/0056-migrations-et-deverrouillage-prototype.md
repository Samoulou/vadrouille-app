## Contexte
Q294 (Samuel, 2026-10-13 22:01 CEST, « Bouton GitHub ») : les migrations passent par un workflow GitHub déclenché à la main par le studio. #283 a cherché à rendre ce workflow sûr par des **contrôles ajoutés à l'exécuteur** : liste des commandes bash admises, interdits arithmétiques, enveloppe `DO … EXECUTE`, ordre insertion / déclencheurs différés / contrôles, puis, pour tenir le verrou S8 sur la base réelle, un relevé du catalogue après chaque migration (droits de `vadrouille_prototype`, rôles « capables », extensions, déclencheurs différés, empreintes des fonctions). Quatre revues consolidées ont chacune trouvé de nouveaux détours (vue sans `security_invoker`, `ALTER EXTENSION … ADD FUNCTION`, fonction en droits de l'invoqueur appelée par une fonction `SECURITY DEFINER`, appartenances transitives, `pg_default_acl`, `pg_db_role_setting`, évaluation arithmétique de `[[ -gt ]]`), puis un visa Sécurité qui ne liait pas le commit appliqué.

**Leçon (Sécu, TL).** La classe « ce qu'un SQL arbitraire peut faire sous `vadrouille_migrator` » est ouverte : la détecter après coup donne un texte sans fin et une fausse assurance. Cette décision inverse l'approche : **refus par défaut** ; seul passe un SQL dont l'empreinte a été **approuvée par Samuel** dans un fichier que 0035 protège déjà. L'exécuteur ne juge plus le SQL ; il vérifie une égalité d'empreintes.

## Décision

### 1. Principe (Sécu) — S9 révisée
**S9 — Aucune migration n'atteint la base réelle sans que son nom et son empreinte SHA-256 figurent dans la liste d'approbation écrite dans `.github/workflows/db-migrate.yml`, que seul Samuel approuve (`owner-approved`, 0035). Le workflow n'exécute aucun fichier du dépôt et n'envoie à la base que des textes dont l'empreinte est dans la liste. Tout le reste est refusé.**

Conséquences directes :
1. **Lancer est sans risque propre** : un lancement n'applique que des migrations déjà approuvées ; le moment du clic n'a plus à être lié à un visa (bloquant 1 du head `10406b4` résolu par construction).
2. **Le verrou S8 sur la base réelle est la liste** : aucune migration qui lève S8, directement ou par un détour, n'est appliquée sans que Samuel ait approuvé son empreinte (§ 3). Les détours de #283 deviennent des motifs de refus du verdict Sécurité qui accompagne l'approbation, pas des contrôles de l'exécuteur (bloquant 2 du head `10406b4`).
3. **Le déverrouillage est l'approbation d'une migration d'une instruction** (§ 4) : ni constante dédiée, ni exception dans l'exécuteur.

### 2. Workflow `db-migrate` (exigences : Sécu ; architecture et outillage : TL)
1. **Fichier** `.github/workflows/db-migrate.yml`. **Déclencheur** : `workflow_dispatch` seul, avec **un seul `inputs`**, `sha_attendu` (obligatoire, chaîne). Aucun autre déclencheur.
2. **Branche** : `if: github.ref == 'refs/heads/main'` sur le job, **et** environnement `db-migrate` dont la règle de déploiement n'admet que la branche `main`. C'est l'environnement qui ferme les secrets : un lancement depuis une autre branche exécute le YAML de cette branche, mais GitHub lui refuse l'environnement.
3. **Commit lancé** : l'étape refuse, avant toute connexion, si `sha_attendu` ne suit pas `^[0-9a-f]{40}$` ou diffère de `$GITHUB_SHA` (comparaison `[[ "$sha_attendu" == "$GITHUB_SHA" ]]`). L'entrée passe par `env:` (`SHA_ATTENDU: ${{ inputs.sha_attendu }}`) ; **aucune expression `${{ … }}` d'entrée ni de contexte modifiable dans un bloc `run:`** (injection de script). Le commit consigné est ainsi celui qui a tourné.
4. **Liste d'approbation** : une constante `MIGRATIONS_APPROUVEES`, écrite en clair dans le bloc `run:`, une ligne `<tag> <sha256>` par migration, **dans l'ordre du journal, en ajout seulement** (vérifié mécaniquement par le test `ci: liste approuvée en ajout seulement` du § 3.4, contre le commit de base de la PR). C'est **la seule source** des noms de migration : le workflow **ne lit pas** `db/migrations/meta/_journal.json`. Chaque ligne est vérifiée (`^[0-9]{4}_[a-z0-9_]{1,60} [0-9a-f]{64}$`) ; une ligne hors forme fait échouer le job.
5. **Code exécuté** :
   - `actions/checkout` épinglé par commit (celui de `ci.yml`), `ref: ${{ github.sha }}`, `persist-credentials: false`, `fetch-depth: 1`, sans sous-module ni LFS ; **aucune autre action** ;
   - aucune commande qui exécute ou charge un fichier du dépôt (`pnpm`, `npm`, `npx`, `node`, `corepack`, `tsx`, `make`, `source`, `.`, `bash <fichier>`, `psql -f`, entrée redirigée vers `psql`) ; commandes externes admises : `sha256sum`, `stat`, `realpath`, `psql -X` ; commandes internes de bash usuelles, sans `eval`, `exec`, `trap`, `export`, `declare`, `let`, `(( ))`, `$(( ))` ;
   - **aucune valeur venue du dépôt n'entre dans une commande avant que son empreinte soit vérifiée** : le texte d'une migration est lu, haché, comparé à la liste, puis seulement envoyé ; une comparaison numérique ne porte que sur `${#…}` ou sur une sortie de `stat` vérifiée auparavant par `^(0|[1-9][0-9]{0,8})$`, sans réaffectation entre la vérification et la comparaison. Comme le journal n'est pas lu, aucune valeur modifiable par une PR ordinaire n'atteint bash avant la vérification d'empreinte (le relevé `a[$(touch …)]` du head `753922b` n'a plus d'entrée).
6. **Une étape, dans cet ordre** (TL : une seule étape suffit, puisque les contrôles n'interprètent aucune donnée non approuvée ; ils précèdent toute connexion). `env:` de l'étape : `SHA_ATTENDU`, `LC_ALL: C`, `PGHOST`, `PGDATABASE`, `PGPASSWORD` (secrets de l'environnement `db-migrate`, noms proposés `MIGRATOR_PGHOST`, `MIGRATOR_PGDATABASE`, `MIGRATOR_PGPASSWORD`), `PGUSER: vadrouille_migrator`, `PGSSLMODE: verify-full`, `PGSSLROOTCERT: system` ; aucune autre variable `PG*`, ni `DATABASE_URL`, ni `VADROUILLE_DATABASE_URL*`.
   1. **Contrôles, sans connexion** : point 3 ; `psql --version` de version majeure 16 ou plus (`sslrootcert=system`, Q388) ; `PGHOST` suit `^[a-z0-9.-]{1,253}$` et `PGDATABASE` `^[a-z0-9_]{1,63}$` ; pour chaque ligne de la liste : le chemin résolu par `realpath -e` est exactement `$GITHUB_WORKSPACE/db/migrations/<tag>.sql` (aucun lien symbolique), fichier ordinaire, non vide, de 100 Kio au plus (limite d'un argument sous Linux : 128 Kio) ; **une seule lecture du fichier par migration**, dans cette forme exacte : `if IFS= read -r -d '' texte < "$f"; then` échec (« octet NUL ») `; fi` — `read -r -d ''` ne rend 0 que s'il a trouvé un octet NUL ; à la fin du fichier sans NUL il rend 1 et `texte` contient tout le fichier ; `${#texte}` égal à la taille donnée par `stat` (un texte tronqué échoue) ; **empreinte de cette même variable** (`printf '%s' "$texte" | sha256sum`) **égale à celle de la liste** ; premier caractère différent de `\`. Le texte vérifié est gardé dans une variable par migration (tableau indexé par la position dans la liste, rempli à cette étape seulement) ; **aucune relecture du disque ensuite** : ni `cat`, ni `$(< …)`, ni seconde redirection depuis `$f`. Tout écart : échec, aucune connexion, rien n'est appliqué, même pour les lignes précédentes.
   2. **Connexion et rôle** : première requête (`SET search_path = pg_catalog, pg_temp` puis bloc `DO`) : `session_user` et `current_user` valent `vadrouille_migrator`, ni `rolsuper` ni `rolbypassrls`, `ssl` vrai dans `pg_catalog.pg_stat_ssl` pour son processus ; sinon exception.
   3. **Journal** : `CREATE TABLE IF NOT EXISTS vadrouille_migrations.applied …` identique à `db/migrate.ts`, puis lecture des `(tag, sha256)` en `psql -X -A -t -F '|'` ; chaque ligne doit suivre `^([0-9]{4}_[a-z0-9_]{1,60})\|([0-9a-f]{64})$`, sinon échec.
   4. **Application, dans l'ordre de la liste** : déjà appliquée avec la même empreinte, ignorée ; avec une autre, échec (« écrire une nouvelle migration ») ; sinon **une session `psql -X -v ON_ERROR_STOP=1 -v VERBOSITY=sqlstate`** formée de `-c` successifs, **dans l'ordre de `db/migrate.ts`** :
      1. `SET lock_timeout = '10s'; SET statement_timeout = '5min'` (une migration qui attend un verrou échoue au lieu de bloquer l'application ; 5 minutes laissent la marge du `timeout-minutes: 10` du job) ;
      2. `BEGIN` ;
      3. `SET LOCAL search_path = pg_catalog, pg_temp` ; verrou consultatif `pg_catalog.pg_advisory_xact_lock(pg_catalog.hashtext('vadrouille_migrations'))` ; repère de transaction `pg_catalog.set_config('vadrouille_migrate.txid', pg_catalog.txid_current()::text, true)` ;
      4. **contrôle, en bloc `DO` qui lève une exception** : le `tag` n'est pas dans `vadrouille_migrations.applied` (un `-c SELECT` ne ferait pas échouer `psql`) ;
      5. **le texte de la migration en un seul `-c`**, la variable vérifiée à l'étape 1, telle quelle (un `-c` est envoyé au serveur sans interprétation des méta-commandes ni des variables de `psql` ; le premier caractère n'est pas `\`) ;
      6. `SET LOCAL search_path = pg_catalog, pg_temp`, puis **contrôle, en bloc `DO` qui lève une exception** : `session_user` et `current_user` valent `vadrouille_migrator` (un `SET ROLE` ou `SET SESSION AUTHORIZATION` non local est vu) ; `pg_catalog.current_setting('session_replication_role')` vaut `origin` ; `pg_catalog.current_setting('vadrouille_migrate.txid', true)` égale `pg_catalog.txid_current()::text` (un `COMMIT` ou un `ROLLBACK` dans le texte efface le repère local : échec ; ce qui précède un `COMMIT` reste validé sans être journalisé : incident traité comme un lot partiel, G2 devant l'avoir refusé) ;
      7. insertion `(tag, sha256)` par `INSERT INTO vadrouille_migrations.applied …`, toutes les fonctions appelées qualifiées par `pg_catalog.` ;
      8. `COMMIT`.

      Une erreur arrête `psql` avant le `COMMIT` et la déconnexion annule la migration en cours. Un `SET` non local laissé par le texte (`search_path`, paramètre de session) meurt avec la session, ouverte pour cette seule migration. **Lot partiel** : chaque migration a sa session et sa transaction ; si la troisième d'un lot échoue, les deux premières restent appliquées et journalisées, la troisième ne laisse rien, les suivantes ne sont pas tentées. Conduite : le lanceur consigne le run (§ 2.9) et prévient la Sécurité et le data ; aucun nouveau lancement avant l'analyse ; la correction est une PR de workflow qui modifie le fichier en échec et **remplace son empreinte dans la liste**, seule exception à l'ajout seulement (§ 3.4), avec un nouveau verdict ; un lancement ultérieur reprend à cette migration. Un échec par délai (`lock_timeout`, `statement_timeout`) suit la même conduite, sans modification du fichier si l'analyse conclut à une attente passagère.
   5. **Sortie** : la sortie standard et d'erreur de chaque `psql` vont dans un fichier de `$RUNNER_TEMP`, jamais affiché ni téléversé (une erreur de connexion nomme l'hôte) ; le job n'affiche que les noms appliqués et ignorés, le nombre de lignes de la liste, et en cas d'échec le `tag`, le code de sortie et le seul SQLSTATE, extrait par `while IFS= read -r ligne; do if [[ $ligne =~ ^(ERROR|FATAL):\ +([0-9A-Z]{5})$ ]]; then …; fi; done`. Ni `set -x`, ni affichage de l'environnement.
7. **(TL, Q388)** `permissions: {}` au niveau du workflow ; `contents: read` au niveau du job, pour `actions/checkout` (lecture d'un dépôt public : aucune exposition ajoutée). `runs-on: ubuntu-24.04`, `timeout-minutes: 10`, `concurrency: { group: db-migrate, cancel-in-progress: false }`.
8. **`db/migrate.ts` ne parle qu'à une base locale** : la PR du workflow le modifie pour refuser tout hôte autre que `localhost`, `127.0.0.1` ou `::1`, après analyse de la chaîne par `pg-connection-string` (hôte de l'URL, `?host=`, plusieurs hôtes, socket, forme `clé=valeur`, hôte absent avec `PGHOST`). Ce refus ferme l'autre chemin vers la base réelle (`pnpm db:migrate`, qui exécuterait le code du dépôt avec le secret). Il reste compatible avec la base de service de la CI : `ci.yml` y pose `PGHOST: 127.0.0.1` (relu sur `a8a3f84`, lignes 54 et 64) et `scripts/ci/db-setup.sh` construit `VADROUILLE_DATABASE_URL_MIGRATOR` sur cet hôte avant `pnpm -s db:migrate` ; la CI de la PR du workflow, qui applique les migrations avec ce refus actif, le vérifie. La même PR met à jour `db/README.md` (§ 2, étape 7 : « Application à la base Neon : par `db-migrate.yml`, lancé à la main sur `main` (Q294 ; décision 0056), qui n'applique que les migrations approuvées ; jamais depuis l'application, la construction Vercel ni `db/migrate.ts` » ; § 3, « Ce que le studio ne fait pas » : « il n'applique de migration que par ce workflow »).
9. **Qui lance** : le rôle que le CEO désigne (proposition : data), avec `sha_attendu` = tête de `main` relevée juste avant. Pas de visa par lancement (l'approbation est par migration, § 3). Après chaque lancement, il consigne dans le ticket ou la PR : conclusion du run, commit, migrations appliquées et ignorées, sans valeur secrète.
10. **Environnement et secrets** : créés et posés **par Samuel**, sauf s'il étend Q321 (alors par le studio selon S5 de 0046) — Q387, inchangée. Le mot de passe est celui de `vadrouille_migrator`, jamais celui de l'identifiant propriétaire de l'intégration Neon. **Aucun agent ne modifie l'environnement `db-migrate`, sa règle de branche ni ses secrets** après leur création. Relevé (noms seulement : règle de branche, secrets de l'environnement et du dépôt) **proposé à Samuel, à la création et après chaque changement qu'il fait**, le mandataire des sessions d'agent refusant ces chemins (Q394 : proposition qui attend sa réponse écrite ; sans elle, la condition 4 du § 4.1 n'est pas réunie) ; il n'est plus exigé avant chaque lancement : un élargissement de la règle exposerait les secrets à toute heure, indépendamment des lancements, et un relevé par lancement ne le fermerait pas.
11. **Relevé du catalogue en lecture, par le studio (Sécu ; outillage : TL)** — `.github/workflows/db-releve.yml`, livré par la PR du workflow (PR de workflow, `owner-approved`), pour les relevés que 0052 (question ouverte 5) attribuait à Samuel :
    - déclencheur `workflow_dispatch` seul, sans `inputs` ; `if: github.ref == 'refs/heads/main'` ; environnement `p0-purge` (règle de branche `main` seule, secrets déjà prévus par 0046) ; `permissions: {}` ; aucune action, ni checkout : le job n'a aucun fichier du dépôt ; `PGSSLMODE: verify-full`, `PGSSLROOTCERT: system` ;

Le catalogue est lisible par tout rôle connecté ; aucune donnée de table n'est lue, donc ni donnée Google ni donnée personnelle ;

### 3. Approbation d'une migration (Sécu ; procédure)
1. **PR d'approbation** : une PR de workflow qui **ajoute** à `MIGRATIONS_APPROUVEES` les lignes de migrations déjà sur `main` ou ajoutées par la même PR. Elle attend `owner-approved`, posé par Samuel (0035) ; tout changement ultérieur de la liste retire le libellé. Rien d'autre n'y change le comportement du workflow. Seule exception à l'ajout : le remplacement de l'empreinte d'une migration dont un run a échoué sans l'appliquer (§ 2.6.4, « Lot partiel ») ; la PR cite ce run.
2. **Description** : pour chaque migration, le `tag`, l'empreinte, le lien vers son diff, la CI verte sur le head, et le **verdict Sécurité selon la grille fermée** ci-dessous. Le CEO la signale dans `#studio` (0035) ; « Nouvelles questions » : « Samuel : owner-approved attendu (décision 0035) ».
3. **Grille du verdict, refus par défaut.** Le verdict porte sur tout ce que le SQL approuvé peut faire sous `vadrouille_migrator` (héritier de `vadrouille_owner`, avec `ADMIN` sur les `vadrouille_fn_*`), pas seulement sur S8. Il est « accordé » seulement si chacun des points G1 à G6 est « oui » :
   - **G1 (verrou S8 et `vadrouille_prototype`)** — la migration ne donne à `vadrouille_prototype` **aucun droit hors de la liste fermée de 0046 (D15 point 6)**, par aucun des chemins suivants, chacun examiné :
     1. droit accordé directement à `vadrouille_prototype` ;
     2. droit accordé à `PUBLIC` ;
     3. appartenance de `vadrouille_prototype` à un autre rôle ;
     4. privilèges par défaut (`ALTER DEFAULT PRIVILEGES`) qui le visent, lui ou `PUBLIC` ;
     5. code exécuté sous un autre rôle et appelable par lui : fonction `SECURITY DEFINER`, vue sans `security_invoker`, déclencheur, règle, politique, valeur par défaut, fonction d'extension ;

     seule exception : la migration de déverrouillage du § 4 ;
   - **G2 (intégrité de l'exécuteur)** — elle ne contient, **au niveau SQL du script** (hors corps de fonction ou de bloc `DO` délimité par `$…$`, et hors `BEGIN ATOMIC … END`), aucune instruction de contrôle de transaction : `BEGIN`, `START TRANSACTION`, `END`, `COMMIT`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE`, `PREPARE TRANSACTION`, `COMMIT AND CHAIN` ; dans un corps plpgsql ou une procédure, aucun `COMMIT` ni `ROLLBACK` ; ni objet du schéma `vadrouille_migrations`, ni `ALTER ROLE` ou `ALTER DATABASE … SET`, ni `CREATE EXTENSION`, ni instruction `SET` de niveau script autre que `SET LOCAL` (la clause `SET search_path` d'une définition de fonction est admise ; `RESET ROLE` aussi), ni `set_config` non local ou du paramètre `vadrouille_migrate.txid`, ni appartenance à un rôle `vadrouille_fn_*` qui survive à la migration (modèle de `0001_securite.sql` : accordée, utilisée, révoquée `GRANTED BY vadrouille_migrator`). Les `BEGIN` et `END` des corps plpgsql de `0001_securite.sql`, `0002_place_coordinates.sql` et `0003_prototype.sql` sont donc admis ;
