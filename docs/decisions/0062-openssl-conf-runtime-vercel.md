## 2. Pourquoi le runtime pose `OPENSSL_CONF` : ce qui est établi, ce qui ne l'est pas

> Conclusion corrigée par 0065 § 2 point 2 (`docs/decisions/0065-nodejs-conf-runtime-vercel.md`) : le `bootstrap` de l'image publique du runtime Lambda pose `OPENSSL_CONF`.

Sources lues le 2026-10-14, relues par le Tech Lead le même jour vers 20:25 UTC.

- **Vercel** ([Reserved environment variables](https://vercel.com/docs/environment-variables/reserved-environment-variables), mise à jour du 2025-12-10 ; recherche dans la documentation par le MCP Vercel, `search_vercel_documentation`, sujet « `OPENSSL_CONF` ») : aucune page ne nomme `OPENSSL_CONF`, ni aucune variable OpenSSL ou TLS. Les variables réservées sont celles de Lambda (`AWS_LAMBDA_*`, `LAMBDA_TASK_ROOT`, `LAMBDA_RUNTIME_DIR`, `TZ`).
- **AWS Lambda** : l'image de base publique du runtime `nodejs24.x` ([`Dockerfile.nodejs24.x`](https://raw.githubusercontent.com/aws/aws-lambda-base-images/nodejs24.x/Dockerfile.nodejs24.x), branche `nodejs24.x` d'`aws/aws-lambda-base-images`) ne pose que `LANG`, `TZ`, `PATH`, `LD_LIBRARY_PATH`, `LAMBDA_TASK_ROOT` et `LAMBDA_RUNTIME_DIR` ; aucune ligne ne mentionne OpenSSL (relu : six couches `ADD`, puis ces six `ENV`). La page [Building Lambda functions with Node.js](https://docs.aws.amazon.com/lambda/latest/dg/lambda-nodejs.html) ne parle que de `NODE_EXTRA_CA_CERTS`. Le runtime Node 24 de Lambda repose sur Amazon Linux 2023 ([annonce AWS](https://aws.amazon.com/blogs/compute/node-js-24-runtime-now-available-in-aws-lambda/)).
- **Node.js 24** ([`doc/api/cli.md`](https://github.com/nodejs/node/blob/v24.x/doc/api/cli.md), section « `OPENSSL_CONF=file` ») : la variable fait charger un fichier de configuration OpenSSL au démarrage ; une valeur vide fait démarrer Node sans fichier, « a way past a default configuration file that exists but cannot be read, for example when `/etc/ssl` is not accessible to the user Node.js runs as, which is otherwise fatal at startup ».
- **Conclusion** : la variable est posée par la plateforme (Vercel ou l'hôte Lambda, pas l'image publique) ; **pourquoi, et vers quel fichier, n'est pas établi**. Hypothèse plausible, non établie : pointer Node vers un fichier lisible (ou vers celui d'Amazon Linux 2023) pour éviter l'échec au démarrage que la documentation de Node décrit. La décision ne repose **pas** sur cette hypothèse : contrairement à 0058, elle n'exige pas de deviner un chemin exact, elle vérifie ce que le fichier peut faire (section 4).

## 3. Ce qu'une configuration OpenSSL peut changer à la vérification TLS (risque réel)

1. **Ce que la configuration peut faire** ([`config(5)`](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man5/config.pod) et [`SSL_CONF_cmd(3)`](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CONF_cmd.pod), OpenSSL 3.5) : charger ou retirer des fournisseurs (`legacy`, `fips`, un fournisseur tiers par `OPENSSL_MODULES`), fixer des propriétés d'algorithmes par défaut, et surtout, par `ssl_conf` et la section **`system_default`**, « applied whenever an `SSL_CTX` object is created » : `MinProtocol` (jusqu'à `TLSv1`), `CipherString`, `Options`, `VerifyMode`, et **`VerifyCAFile` / `VerifyCAPath`**, qui ajoutent des autorités de vérification. Un fichier peut en inclure d'autres (`.include`, fichier ou dossier dont OpenSSL lit les fichiers terminés par `.cnf` ou `.conf`, **casse ignorée** : `OPENSSL_strcasecmp` dans [`crypto/conf/conf_def.c`](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/conf/conf_def.c) ; chemins relatifs résolus par `OPENSSL_CONF_INCLUDE`, par `.pragma includedir` ou par le répertoire courant ; variables `$…` développées dans le chemin). Le risque réel est donc : TLS rétrogradé, suites faibles, ou une autorité ajoutée qui permet une interception — exactement ce que la barrière refuse.
2. **Ce que Node en applique** ([`doc/api/crypto.md`](https://github.com/nodejs/node/blob/v24.x/doc/api/crypto.md), section FIPS ; [`src/node.cc`](https://github.com/nodejs/node/blob/v24.x/src/node.cc), initialisation d'OpenSSL) : « By default, Node.js reads the `nodejs_conf` section instead of OpenSSL's usual `openssl_conf` section » ; `--openssl-shared-config` rétablit `openssl_conf`. Dans le code, Node lit `OPENSSL_CONF` **une fois, au démarrage** (`credentials::SafeGetenv("OPENSSL_CONF", …)`), puis appelle `OPENSSL_INIT_set_config_appname(settings, conf_section_name)` avec les seuls drapeaux `CONF_MFLAGS_IGNORE_MISSING_FILE` ; or OpenSSL ([`crypto/conf/conf_mod.c`](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/conf/conf_mod.c), l. 146-150) ne se rabat sur `openssl_conf` que si `CONF_MFLAGS_DEFAULT_SECTION` est posé. **Conséquence établie, pour une construction de Node aux options par défaut** : un fichier (inclusions comprises) qui ne définit pas la clé `nodejs_conf` dans sa section par défaut n'a **aucun effet** sur la configuration OpenSSL de Node, donc aucun sur TLS. Le fichier doit seulement se lire sans erreur (sinon Node refuse de démarrer).
   **Limite relevée à la relecture (Tech Lead, correction 1)** : `conf_section_name` vaut `NODE_OPENSSL_CONF_NAME`, fixé **à la construction** de Node (`configure.py`, option `--openssl-conf-name`, valeur par défaut `nodejs_conf`). Une construction de Node qui changerait ce nom lirait une autre section. Les binaires officiels de Node gardent la valeur par défaut ; les options de construction du binaire de `nodejs24.x` (Lambda ou Vercel) **ne sont pas établies**. **Correction (revue Sécurité du head `b0c1c45`, bloquant 1)** : contrairement à ce qu'écrivait cette section, le nom est **observable depuis JavaScript** : `configure.py` ajoute `NODE_OPENSSL_CONF_NAME=…` aux `defines`, qui aboutissent dans `process.config.target_defaults.defines` (vérifié sous Node 22 : `NODE_OPENSSL_CONF_NAME=nodejs_conf`). La condition 1.7 de la section 4 le vérifie ; le risque résiduel (c) de la section 6 en est réduit.
3. **Sans `OPENSSL_CONF`**, Node lit déjà le fichier par défaut d'OpenSSL (`OPENSSLDIR`), avec la même règle `nodejs_conf`. La barrière n'a jamais contrôlé ce fichier-là ; la variable ne fait que changer le fichier lu. Le danger n'est pas la variable, c'est un fichier qui définirait `nodejs_conf`, ou un fichier inscriptible par la fonction (sur Lambda, seul `/tmp` l'est).
4. **Options de Node** : `--openssl-shared-config` et `--openssl-config` restent interdites (`OPTIONS_TLS`, inchangé), dans `NODE_OPTIONS` et `execArgv` ; une forme niée échoue fermée. La règle `nodejs_conf` ci-dessus vaut donc au runtime, sous la limite du point 2.

## 4. Décision (TL) : exception bornée, vérifiée sur le contenu du fichier

**Effective seulement après l'avis de la Sécurité** (statut). Ce que la barrière protège : une **mauvaise configuration** de la plateforme ou du projet. Elle ne protège pas contre un code applicatif hostile, qui s'exécute dans le même processus et peut modifier `process.env` ou contourner la barrière de bien d'autres façons.

1. **Le cas admis, et lui seul**. `OPENSSL_CONF` posée est admise si **toutes** les conditions suivantes sont vraies, sinon la barrière rend `tls_env_refused` comme aujourd'hui :
   1. `VERCEL` égale à `1` et `VERCEL_ENV` égale à `preview`, comparaison exacte, **dans l'environnement lu et dans le vrai `process.env`** (D21 de 0046) ; la règle de production est contrôlée avant et inchangée ;
   2. la valeur de l'environnement lu est **identique** à celle du vrai `process.env`, toutes deux lues **à l'appel**. Cette condition garantit seulement la **cohérence des deux lectures** (l'environnement injecté ne peut que resserrer). Elle ne garantit **pas** que le fichier examiné soit celui que Node a chargé : Node a lu `OPENSSL_CONF` une seule fois, au démarrage (section 3.2), et le code applicatif peut modifier `process.env.OPENSSL_CONF` entre-temps. Risque résiduel (b) de la section 6 ;
   3. **chemin** : absolu, canonique (égal à sa forme normalisée POSIX, `posix.normalize` : ni `.`, ni `..`, ni `//`, ni `/` final), sans espace, sans `$`, sans `\`, sans guillemet, sans caractère de contrôle ; soit exactement `/dev/null`, soit sous l'une des racines en lecture seule du runtime : `/etc/`, `/usr/`, `/var/runtime/`, `/var/lang/` (`/opt/`, écrit ici d'abord, est retiré par la PR de code : voir les Précisions). Tout le reste est refusé, notamment `/tmp/`, `/var/task/` (le paquet de la fonction) et `/proc/` ;
   4. **fichier** : hors `/dev/null`, le chemin réel (`realpath`) est sous les mêmes racines, c'est un fichier ordinaire, lisible, d'au plus 64 Kio ;
   5. **contenu** : après jonction des lignes continuées (`\` en fin de ligne, dans l'ordre d'OpenSSL : jonction d'abord, commentaires ensuite) puis retrait de tous les `\`, le texte ne contient **nulle part**, casse ignorée, la chaîne `nodejs_conf` (**commentaires compris** : un faux positif refuse, échec fermé) ;
   6. **inclusions** : l'analyse porte sur le texte joint (avant retrait des `\`). Une ligne dont le premier caractère non blanc est `#` est un commentaire entier et est **ignorée pour les inclusions seulement** (OpenSSL retire les commentaires avant de reconnaître `.include` ; la recherche du point 5 la lit toujours). Dans toute autre ligne, chaque occurrence de `.include` (casse ignorée) doit être une directive entière : blancs éventuels, `.include`, puis `=` ou un blanc, puis un chemin absolu fait seulement de caractères autres que blancs, `$`, `\`, guillemets et `#`, soumis aux points 3 et 4. Un `.include` dans un commentaire de fin de ligne est donc refusé (coût assumé : échec fermé). Un dossier est admis s'il est sous les mêmes racines ; au plus **64 entrées** y sont listées (au-delà : refus) ; chacune dont le nom se termine par `.cnf` ou `.conf`, **casse ignorée comme OpenSSL** (un `X.CNF` non examiné serait chargé par Node), est examinée (points 4 à 6), et doit être un fichier ordinaire. Profondeur d'inclusion au plus 2, au plus 16 fichiers examinés en tout. Une directive mal formée, un chemin relatif, un `$`, un `\`, une profondeur ou un nombre dépassé : refus. Une ligne `.pragma` est sans effet sur ces règles (`includedir` ne sert qu'aux chemins relatifs, refusés).
   7. **construction de Node** (ajoutée par la PR de code, bloquant 1 de la revue Sécurité du head `b0c1c45`) : `process.config.target_defaults.defines` contient exactement `NODE_OPENSSL_CONF_NAME=nodejs_conf` et aucune autre entrée commençant par `NODE_OPENSSL_CONF_NAME=` ; `process.config`, `target_defaults` ou `defines` absent ou de forme inattendue (pas un objet, pas un tableau de chaînes) : refus. Jugée après 1.2 et avant 1.3, sans accès au système de fichiers ; `process.config` est injectable pour les tests (cinquième paramètre de `verifierSortie`).
2. **Toujours refusé, comme avant** : toute autre variable TLS posée, même seule (`NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `SSLKEYLOGFILE`) ; toute option TLS interdite ; tout proxy. `OPENSSL_CONF` admise ne masque ni la production, ni un proxy, ni une autre cause TLS.
3. **Retrait de l'exception de 0058 § 4** (`NODE_EXTRA_CA_CERTS=/var/runtime/ca-cert.pem`) : réfutée par le relevé, elle n'a jamais servi ; la garder élargirait la barrière sans besoin. Retrait effectif **dès la fusion de 0062** (il ne fait que resserrer) ; le code (`CHEMIN_CA_RUNTIME_VERCEL`, `exceptionCaRuntime`, la marque `vercel_runtime_ca`) est retiré par la PR de code ; `NODE_EXTRA_CA_CERTS` redevient refusée sans exception.
4. **Portée** : la barrière entière (les modules de capacité `ai.ts`, `grounding.ts`, `undici-transport.ts` et `p0.ts`), en préversion seulement. À réexaminer à la passe de sécurité qui précède la mise en public (0034, point 1).
5. **Coût** : le code est **synchrone**, parce que `verifierSortie` l'est (à la différence de `src/adapters/prototype-loader.ts`, asynchrone, `node:fs/promises`). Au pire, par appel : 16 fichiers lus (64 Kio chacun), leurs `lstat` et `realpath`, et les listes de dossiers (64 entrées chacune). **Pas de mémoïsation** dans cette décision : le coût est borné, la barrière n'est appelée qu'en préversion de `p0-reel` ; **correction (PR de code, mineur 1)** : l'examen s'exécute à chaque appel de `verifierSortie`, donc aussi à chaque GET de la page de saisie et à chaque action (`src/server/p0/acces.ts`, `etatPageAcces` et `ouvertureP0`), pas seulement à la construction d'un client réel ; coût toujours borné. Un cache par chemin serait sûr (racines non inscriptibles par la fonction) ; à décider sur mesure si la latence le demande, avec le système de fichiers réel seulement.
6. **Pourquoi pas une autre voie** :
   - _Chemin exact deviné (forme de 0058 § 4)_ : aucune source ne donne le chemin ; un nouveau tour de relevé pour l'apprendre, puis un autre pour l'admettre, et l'égalité de chemin ne dit rien du contenu. Le contenu est ce qui compte (section 3).
   - _Vider la variable au démarrage_ : sans effet, Node lit `OPENSSL_CONF` avant le code de l'application.
   - _Vérifier l'état effectif_ (`tls.DEFAULT_MIN_VERSION`, `crypto.getFips()`) : partiel ; `system_default` (`VerifyCAFile`, `CipherString`) n'est pas observable depuis JavaScript.
   - _Retirer `OPENSSL_CONF` de la liste_ : refusé par S-1 point 4 ; un fichier hors runtime ou définissant `nodejs_conf` doit rester bloquant.

## 5. Diagnostic (TL ; amende 0058 § 3)

> Verdict `contenu_audite` et champ `openssl_conf_directives` ajoutés par 0065 (`docs/decisions/0065-nodejs-conf-runtime-vercel.md`, section 4 points 2 et 3).

La zone est alors toujours rendue, verdict `hors_preview` compris. En cas de refus de proxy, le fichier n'est pas lu et les deux champs sont absents.

3. `src/server/log.ts` admet ces champs, chacun contrôlé contre sa liste fermée ; toute autre valeur est retirée (`dropped`). L'égalité des listes du journal et d'`egress.ts` est vérifiée par `tests/unit/p0/garde.test.ts`, sur le modèle de `LOG_EXIT_CAUSES`.
4. Le diagnostic ne relit pas l'environnement : il réutilise les deux lectures de la condition 1.2 (la lecture de l'environnement reçu, et la seule lecture ajoutée, `process.env.OPENSSL_CONF` par propriété littérale dans `deploiementReel`, patron D21 de `egress.ts`). Le fichier est lu dans l'appel, paresseusement, seulement si `OPENSSL_CONF` est posée et que les conditions 1.1, 1.2, 1.7 et 1.3 passent.

## 6. Analyse du Tech Lead, avis Sécurité à rendre

_Rédigée par le **Tech Lead**, auteur de cette décision, en suivant la grille du rôle Sécurité (`.claude/agents/securite.md` : RLS, secrets, dépendances, règles Google, données personnelles ; en cas de doute, changements demandés). **Ce n'est pas un avis de la Sécurité** et cela ne remplit pas 0055 S-1 point 4 : l'auteur d'une décision ne peut pas en être le contrôleur indépendant. L'avis de la Sécurité est à rendre sur cette section, au plus tard à la revue de la PR de code ; il peut la contredire en tout ou partie. Sans lui, l'exception de la section 4 n'est pas effective._

**Proposition du Tech Lead à la Sécurité** : accepter, avec les conditions ci-dessous.

1. **Analyse** : section 3. Le comportement « `nodejs_conf` seulement » est établi par la documentation **et** par le code de Node 24 et d'OpenSSL 3.5, relus le 2026-10-14, **pour une construction de Node aux options par défaut** (limite de la section 3.2). Vérifier le contenu est plus sûr que l'égalité de chemin de 0058 : un fichier qui ne nomme pas `nodejs_conf` ne peut pas affaiblir TLS dans un tel Node, quel que soit son chemin.
2. **Analyse** : le retrait de l'exception de 0058 § 4. Une exception qui n'a jamais servi est une surface sans bénéfice.
3. **Condition proposée (secrets, journal)** : aucune valeur de `OPENSSL_CONF`, aucun extrait du fichier, aucun nom de fichier inclus, aucune taille ni condensat dans le journal, les erreurs ou les tests (test sentinelle : une valeur et un contenu marqués n'apparaissent dans aucune ligne écrite). Les erreurs du système de fichiers ne sont jamais propagées : seul le verdict fermé sort, l'exception éventuelle est rattrapée et vaut `fichier_refuse`.
4. **Condition proposée (échec fermé)** : toute erreur de lecture, toute forme non reconnue, tout dépassement de borne refuse. Aucun `trim()` sur le chemin. La recherche de `nodejs_conf` porte sur le texte entier, commentaires compris.
5. **Condition proposée (dépendances, régime de confinement)** : aucune bibliothèque ajoutée ; seulement `node:fs` (synchrone) et `node:path` (`posix.normalize`). `src/server/env/` est une zone sensible du régime (`ZONES_SENSIBLES`, `tests/unit/confinement/analyse.ts:119`), où un fichier non-test n'admet sans ligne que `zod` ; les lignes générales `node:fs` et `node:path` de `tests/unit/confinement/listes/specificateurs.ts:59-60` excluent `@src-non-test` et `@sensible`. Il faut donc **deux lignes nominatives** (fichier, spécificateur, noms exacts), sur le modèle des trois lignes de `src/adapters/prototype-loader.ts` (`specificateurs.ts:155-173`), pour `src/server/env/openssl-conf.ts` seulement :
   - `node:fs`, noms `lstatSync`, `readFileSync`, `readdirSync`, `realpathSync` ;
   - `node:path`, nom `posix` (import `{ posix }`, pour `posix.normalize`).
   - Le type du système de fichiers injectable est déclaré dans le module, sans `import type` depuis `node:fs` (sinon un nom `type:…` de plus). Aucun autre module de `src/server/env/` n'importe `node:fs` ni `node:path`. Ces deux lignes exigent le **verdict de la Sécurité** (en-tête de `specificateurs.ts`) : **à rendre**, avec l'avis.
6. **Risque résiduel proposé à l'acceptation** (préversion de `p0-reel`, derrière la protection Vercel, jusqu'à la passe de sécurité de 0034 point 1) :
   - (a) le fichier par défaut d'OpenSSL (`OPENSSLDIR`), lu même sans la variable, n'est pas contrôlé, comme avant ;
   - (b) **le fichier examiné peut ne pas être celui que Node a chargé** : Node lit `OPENSSL_CONF` une fois au démarrage ; la barrière compare deux lectures faites à l'appel (condition 1.2), que le code applicatif peut avoir modifiées entre-temps ; et la vérification du contenu a lieu après le chargement. Elle n'est sûre que contre une **mauvaise configuration** : racines admises non inscriptibles par la fonction (seul `/tmp` l'est sur Lambda, et il est refusé), et aucun code du projet n'écrit `process.env.OPENSSL_CONF` (le régime de confinement relève toute écriture de `process.env`, `tests/unit/confinement/analyse.ts:861-921`). Contre un code applicatif hostile, la barrière n'est pas une protection, et ne prétend pas l'être ;
   - (c) l'examen ne couvre que la clé `nodejs_conf`. Une construction de Node avec un autre `--openssl-conf-name` est désormais **refusée** par la condition 1.7 (`process.config`, section 3.2 corrigée), et non plus seulement acceptée comme risque.
