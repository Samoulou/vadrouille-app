## 2. Pourquoi le runtime pose `OPENSSL_CONF` : ce qui est établi, ce qui ne l'est pas

Sources lues le 2026-10-14.

- **Vercel** ([Reserved environment variables](https://vercel.com/docs/environment-variables/reserved-environment-variables), mise à jour du 2025-12-10 ; recherche dans la documentation par le MCP Vercel, `search_vercel_documentation`, sujet « OPENSSL_CONF ») : aucune page ne nomme `OPENSSL_CONF`, ni aucune variable OpenSSL ou TLS. Les variables réservées sont celles de Lambda (`AWS_LAMBDA_*`, `LAMBDA_TASK_ROOT`, `LAMBDA_RUNTIME_DIR`, `TZ`).
- **AWS Lambda** : l'image de base publique du runtime `nodejs24.x` ([`Dockerfile.nodejs24.x`](https://raw.githubusercontent.com/aws/aws-lambda-base-images/nodejs24.x/Dockerfile.nodejs24.x), branche `nodejs24.x` d'`aws/aws-lambda-base-images`) ne pose que `LANG`, `TZ`, `PATH`, `LD_LIBRARY_PATH`, `LAMBDA_TASK_ROOT` et `LAMBDA_RUNTIME_DIR` ; aucune ligne ne mentionne OpenSSL. La page [Building Lambda functions with Node.js](https://docs.aws.amazon.com/lambda/latest/dg/lambda-nodejs.html) ne parle que de `NODE_EXTRA_CA_CERTS`. Le runtime Node 24 de Lambda repose sur Amazon Linux 2023 ([annonce AWS](https://aws.amazon.com/blogs/compute/node-js-24-runtime-now-available-in-aws-lambda/)).
- **Node.js 24** ([`doc/api/cli.md`](https://github.com/nodejs/node/blob/v24.x/doc/api/cli.md), section « `OPENSSL_CONF=file` ») : la variable fait charger un fichier de configuration OpenSSL au démarrage ; une valeur vide fait démarrer Node sans fichier, « a way past a default configuration file that exists but cannot be read, for example when `/etc/ssl` is not accessible to the user Node.js runs as, which is otherwise fatal at startup ».
- **Conclusion** : la variable est posée par la plateforme (Vercel ou l'hôte Lambda, pas l'image publique) ; **pourquoi, et vers quel fichier, n'est pas établi**. Hypothèse plausible, non établie : pointer Node vers un fichier lisible (ou vers celui d'Amazon Linux 2023) pour éviter l'échec au démarrage que la documentation de Node décrit. La décision ne repose **pas** sur cette hypothèse : contrairement à 0058, elle n'exige pas de deviner un chemin exact, elle vérifie ce que le fichier peut faire (section 4).

## 3. Ce qu'une configuration OpenSSL peut changer à la vérification TLS (risque réel)

1. **Ce que la configuration peut faire** ([`config(5)`](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man5/config.pod) et [`SSL_CONF_cmd(3)`](https://github.com/openssl/openssl/blob/openssl-3.5/doc/man3/SSL_CONF_cmd.pod), OpenSSL 3.5) : charger ou retirer des fournisseurs (`legacy`, `fips`, un fournisseur tiers par `OPENSSL_MODULES`), fixer des propriétés d'algorithmes par défaut, et surtout, par `ssl_conf` et la section **`system_default`**, « applied whenever an `SSL_CTX` object is created » : `MinProtocol` (jusqu'à `TLSv1`), `CipherString`, `Options`, `VerifyMode`, et **`VerifyCAFile` / `VerifyCAPath`**, qui ajoutent des autorités de vérification. Un fichier peut en inclure d'autres (`.include`, fichier ou dossier de `*.cnf`/`*.conf`, chemins relatifs résolus par `OPENSSL_CONF_INCLUDE` ou le répertoire courant). Le risque réel est donc : TLS rétrogradé, suites faibles, ou une autorité ajoutée qui permet une interception — exactement ce que la barrière refuse.
2. **Ce que Node en applique** ([`doc/api/crypto.md`](https://github.com/nodejs/node/blob/v24.x/doc/api/crypto.md), section FIPS ; [`src/node.cc`](https://github.com/nodejs/node/blob/v24.x/src/node.cc), initialisation d'OpenSSL) : « By default, Node.js reads the `nodejs_conf` section instead of OpenSSL's usual `openssl_conf` section » ; `--openssl-shared-config` rétablit `openssl_conf`. Dans le code, Node appelle `OPENSSL_INIT_set_config_appname(settings, "nodejs_conf")` avec les seuls drapeaux `CONF_MFLAGS_IGNORE_MISSING_FILE` ; or OpenSSL ([`crypto/conf/conf_mod.c`](https://github.com/openssl/openssl/blob/openssl-3.5/crypto/conf/conf_mod.c)) ne se rabat sur `openssl_conf` que si `CONF_MFLAGS_DEFAULT_SECTION` est posé. **Conséquence établie** : un fichier (inclusions comprises) qui ne définit pas la clé `nodejs_conf` dans sa section par défaut n'a **aucun effet** sur la configuration OpenSSL de Node, donc aucun sur TLS. Le fichier doit seulement se lire sans erreur (sinon Node refuse de démarrer).
3. **Sans `OPENSSL_CONF`**, Node lit déjà le fichier par défaut d'OpenSSL (`OPENSSLDIR`), avec la même règle `nodejs_conf`. La barrière n'a jamais contrôlé ce fichier-là ; la variable ne fait que changer le fichier lu. Le danger n'est pas la variable, c'est un fichier qui définirait `nodejs_conf`, ou un fichier inscriptible par la fonction (sur Lambda, seul `/tmp` l'est).
4. **Options de Node** : `--openssl-shared-config` et `--openssl-config` restent interdites (`OPTIONS_TLS`, inchangé), dans `NODE_OPTIONS` et `execArgv` ; une forme niée échoue fermée. La règle `nodejs_conf` ci-dessus vaut donc au runtime.

## 4. Décision (TL) : exception bornée, vérifiée sur le contenu du fichier

1. **Le cas admis, et lui seul**. `OPENSSL_CONF` posée est admise si **toutes** les conditions suivantes sont vraies, sinon la barrière rend `tls_env_refused` comme aujourd'hui :
   1. `VERCEL` égale à `1` et `VERCEL_ENV` égale à `preview`, comparaison exacte, **dans l'environnement lu et dans le vrai `process.env`** (D21 de 0046) ; la règle de production est contrôlée avant et inchangée ;
   2. la valeur de l'environnement lu est **identique** à celle du vrai `process.env` (le fichier examiné est celui que Node a chargé ; l'environnement injecté ne peut que resserrer) ;
   3. **chemin** : absolu, canonique (égal à sa forme normalisée POSIX : ni `.`, ni `..`, ni `//`, ni `/` final), sans espace, sans `$`, sans caractère de contrôle ; soit exactement `/dev/null`, soit sous l'une des racines en lecture seule du runtime : `/etc/`, `/usr/`, `/var/runtime/`, `/var/lang/`, `/opt/`. Tout le reste est refusé, notamment `/tmp/`, `/var/task/` (le paquet de la fonction) et `/proc/` ;
   4. **fichier** : hors `/dev/null`, le chemin réel (`realpath`) est sous les mêmes racines, c'est un fichier ordinaire, lisible, d'au plus 64 Kio ;
   5. **contenu** : après jonction des lignes continuées (`\` en fin de ligne) puis retrait de tous les `\`, le texte ne contient **nulle part**, casse ignorée, la chaîne `nodejs_conf` (commentaires compris : un faux positif refuse, échec fermé) ;
   6. **inclusions** : chaque occurrence de `.include` (casse ignorée) doit être une directive entière `.include [=] <chemin>` en début de ligne, au chemin absolu soumis aux points 3 et 4 ; un dossier est admis s'il est sous les mêmes racines, et chacun de ses fichiers `*.cnf` et `*.conf` est examiné (points 4 à 6) ; profondeur d'inclusion au plus 2, au plus 16 fichiers examinés en tout. Une directive mal formée, un chemin relatif, un `$`, une profondeur ou un nombre dépassé : refus.
2. **Toujours refusé, comme avant** : toute autre variable TLS posée, même seule (`NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `SSLKEYLOGFILE`) ; toute option TLS interdite ; tout proxy. `OPENSSL_CONF` admise ne masque ni la production, ni un proxy, ni une autre cause TLS.
3. **Retrait de l'exception de 0058 § 4** (`NODE_EXTRA_CA_CERTS=/var/runtime/ca-cert.pem`) : réfutée par le relevé, elle n'a jamais servi ; la garder élargirait la barrière sans besoin. `CHEMIN_CA_RUNTIME_VERCEL` et la marque `vercel_runtime_ca` sont retirés ; `NODE_EXTRA_CA_CERTS` redevient refusée sans exception.
4. **Portée** : la barrière entière (les modules de capacité `ai.ts`, `grounding.ts`, `undici-transport.ts` et `p0.ts`), en préversion seulement. À réexaminer à la passe de sécurité qui précède la mise en public (0034, point 1).
5. **Pourquoi pas une autre voie** :
   - *Chemin exact deviné (forme de 0058 § 4)* : aucune source ne donne le chemin ; un nouveau tour de relevé pour l'apprendre, puis un autre pour l'admettre, et l'égalité de chemin ne dit rien du contenu. Le contenu est ce qui compte (section 3).
   - *Vider la variable au démarrage* : sans effet, Node lit `OPENSSL_CONF` avant le code de l'application.
   - *Vérifier l'état effectif* (`tls.DEFAULT_MIN_VERSION`, `crypto.getFips()`) : partiel ; `system_default` (`VerifyCAFile`, `CipherString`) n'est pas observable depuis JavaScript.
   - *Retirer `OPENSSL_CONF` de la liste* : refusé par S-1 point 4 ; un fichier hors runtime ou définissant `nodejs_conf` doit rester bloquant.

## 5. Diagnostic (TL ; amende 0058 § 3)

1. `DiagnosticSortie` gagne deux champs facultatifs, rendus seulement quand `OPENSSL_CONF` est posée, valeurs prises dans des listes fermées, **jamais** une valeur, une longueur, un préfixe ni un condensat :
   - `openssl_conf_zone` : racine du chemin déclaré, `dev_null`, `etc`, `usr`, `var_runtime`, `var_lang`, `opt` ou `autre` ;
   - `openssl_conf_verdict` : `admis`, `env_differente` (point 1.2), `chemin_refuse` (1.3), `fichier_refuse` (1.4 : absent, illisible, pas un fichier ordinaire, trop grand, chemin réel hors racines), `section_nodejs` (1.5), `inclusion_refusee` (1.6), `hors_preview` (1.1).
2. `exception` prend la seule valeur `vercel_runtime_openssl_conf` quand l'exception a servi (remplace `vercel_runtime_ca`).
3. `src/server/log.ts` admet ces champs, chacun contrôlé contre sa liste fermée ; toute autre valeur est retirée (`dropped`). L'égalité des listes du journal et d'`egress.ts` est vérifiée par `tests/unit/p0/garde.test.ts`, sur le modèle de `LOG_EXIT_CAUSES`.
4. Pas de seconde lecture de l'environnement ; le fichier est lu dans l'appel, paresseusement, seulement si `OPENSSL_CONF` est posée et que les conditions 1.1 à 1.3 passent.

## 6. Avis de la Sécurité

*Rédigé par le Tech Lead jouant le rôle de la Sécurité, en appliquant `.claude/agents/securite.md` (RLS, secrets, dépendances, règles Google, données personnelles ; en cas de doute, changements demandés). Ce n'est pas l'avis d'une session Sécurité distincte : la PR de code qui suivra porte sa propre revue Sécurité, qui peut le contredire.*

**Avis : favorable, avec conditions.**

1. **Accepté** : l'analyse de la section 3. Le comportement « `nodejs_conf` seulement » est établi par la documentation **et** par le code de Node 24 et d'OpenSSL 3.5, pas par une hypothèse. Vérifier le contenu est plus sûr que l'égalité de chemin de 0058 : un fichier qui ne nomme pas `nodejs_conf` ne peut pas affaiblir TLS dans Node, quel que soit son chemin.
2. **Accepté** : le retrait de l'exception de 0058 § 4. Une exception qui n'a jamais servi est une surface sans bénéfice.
3. **Condition (secrets, journal)** : aucune valeur de `OPENSSL_CONF`, aucun extrait du fichier, aucun nom de fichier inclus, aucune taille ni condensat dans le journal, les erreurs ou les tests (test sentinelle : une valeur et un contenu marqués n'apparaissent dans aucune ligne écrite). Les erreurs du système de fichiers ne sont jamais propagées : seul le verdict fermé sort, l'exception éventuelle est rattrapée et vaut `fichier_refuse`.
4. **Condition (échec fermé)** : toute erreur de lecture, toute forme non reconnue, tout dépassement de borne refuse. Aucun `trim()` sur le chemin. La recherche de `nodejs_conf` porte sur le texte entier, commentaires compris.
5. **Condition (dépendances)** : aucune bibliothèque ajoutée ; seulement `node:fs` (synchrone) et `node:path` (`posix.normalize`). L'import de `node:fs` dans un fichier non-test de `src/` exige une ligne nominative dans `tests/unit/confinement/listes/specificateurs.ts` (fichier, spécificateur, noms exacts) : **verdict Sécurité accordé ici** pour `src/server/env/openssl-conf.ts` seulement, avec les noms `lstatSync`, `readFileSync`, `readdirSync`, `realpathSync`. Aucun autre module de `src/server/env/` n'importe `node:fs`.
6. **Risque résiduel accepté** (préversion de `p0-reel`, derrière la protection Vercel, jusqu'à la passe de sécurité de 0034 point 1) : (a) le fichier par défaut d'OpenSSL (`OPENSSLDIR`), lu même sans la variable, n'est pas contrôlé, comme avant ; (b) la vérification du contenu a lieu après le chargement par Node : sûre seulement parce que les racines admises ne sont pas inscriptibles par la fonction (seul `/tmp` l'est sur Lambda, et il est refusé) ; (c) l'examen ne couvre que la clé `nodejs_conf` : si une version future de Node changeait la section lue par défaut (règle en vigueur depuis Node 18.5, donc pour `engines` `>=22.19.0` et pour `nodejs24.x`), la règle serait à revoir. Le commentaire d'`openssl-conf.ts` (section 7) le rappelle à chaque changement de version majeure de Node.
7. **Hors de cette décision, rappel** : le relevé du 2026-10-14 confirme le risque de 0055 S-4 point 2 (`P0_RUN_TOKEN` non `sensitive`, signal `readable-secret`). La seconde partie de Q402 reste à présenter à Samuel ; elle ne bloque pas cette décision.
