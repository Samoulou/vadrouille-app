### B3-TL-5 — Mesure et qualité des secrets : forme révisée acceptée par le Tech Lead
La forme révisée de la spécification est retenue telle quelle (décodage hexadécimal d'abord pour une valeur de longueur paire faite de `[0-9a-fA-F]`, sinon base64 ou base64url strict par expression régulière puis aller-retour, sinon refus ; au moins 32 octets décodés ; règles et unicité sur les octets décodés ; refus d'un caractère unique répété, des valeurs triviales et de moins de 16 octets distincts ; « distinct par environnement » laissé à la consigne de `docs/deploiement/variables-environnement.md`). Précisions :
1. **Une seule fonction** `decodeSecret(name, value)` dans `src/server/env.ts`, utilisée pour `RATE_LIMIT_HMAC_SECRET`, puis par B3b pour `BETTER_AUTH_SECRET` et par B4 pour `SIMULATED_WEBHOOK_SECRET` ; elle renvoie un `Buffer` et n'est pas exportée hors de `src/server/env*`. Les modules consommateurs reçoivent les octets décodés, jamais la chaîne.
2. **Base64 strict** : alphabet `A-Za-z0-9+/` avec remplissage `=` correct (longueur multiple de 4), **ou** alphabet `A-Za-z0-9-_` sans remplissage ; jamais un mélange des deux alphabets ; aucun espace ni retour à la ligne, même en fin de chaîne. La valeur reçue est comparée **sans** `trim()` : un espace en bordure est un refus (`secret_encoding`), pas une correction.
3. **Valeurs triviales** : la valeur reçue, en minuscules, est comparée à chaque mot de la liste (`changeme`, `secret`, `password`, `test`, `example`, `vadrouille`) répété jusqu'à sa longueur (préfixe d'une répétition) ; la liste vit dans `src/server/env.ts` et peut être allongée par une PR sans décision nouvelle.
4. **Unicité** : comparée entre tous les secrets présents (octets décodés, `crypto.timingSafeEqual` inutile ici : aucune valeur ne vient d'un client).
5. La **position de la Sécurité** sur ces règles (bloquant 12 de la revue du head `6b17404`, « à confirmer ») est rendue dans **0051** (P5) ; si elle diffère, 0051 prévaut sur les points de sécurité et B3a l'applique.

1. **Message HMAC** (UTF-8, ASCII de fait) : `rl/v1/<action>/<fenêtre>/<espèce>/<valeur>` où
   - `<action>` : nom d'action de la configuration, `^[a-z][a-z0-9-]{0,47}$` (par exemple `request-code`, `verify-code`) ;
   - `<fenêtre>` : durée de la fenêtre en secondes, entier décimal suivi de `s` (`600s`, `3600s`, `86400s`) : deux fenêtres d'une même action donnent deux clés (critère A5) ;
   - `<espèce>/<valeur>` : `ip/<clé d'adresse>` (IPv4 entière en notation pointée ; IPv6 sous la forme `<préfixe /64 canonique compressé en minuscules>/64`, par exemple `2001:db8:1:2::/64`), `email/<clé e-mail>` (B3a point 6 : forme canonique de `parseEmailAddress`, partie locale coupée au premier `+`), ou `no-trusted-ip` seul, sans valeur, pour le compartiment commun. L'e-mail est toujours le dernier élément du message.
2. **Clé stockée** : `HMAC-SHA-256(RATE_LIMIT_HMAC_SECRET décodé, message)` en **hexadécimal minuscule** (64 caractères), comme les autres empreintes du dépôt (`src/adapters/share-token.ts`).
3. **Fenêtre à l'horloge de la base** : un seul `INSERT … ON CONFLICT (key) DO UPDATE` par clé, qui pose `window_start = now()`, `expires_at = now() + make_interval(secs => $durée)` et `count = 1` si `action_rate_limits.expires_at <= now()`, sinon `count = count + 1`, et renvoie `count` ; refus quand `count` dépasse le seuil (le seuil est le nombre d'appels admis). Les clés d'un appel (adresse IP puis e-mail) sont incrémentées dans **une** transaction (`SET LOCAL ROLE vadrouille_limiter`), dans l'ordre fixe de la spécification ; la décision est rendue après la validation de cette transaction.
4. **Purge isolée** : dans une **transaction distincte**, ouverte après la validation de l'incrément, sur le même pool et sous le même rôle, attendue (`await`) mais dont toute erreur est rattrapée : elle n'annule ni ne change la décision, et écrit `rate_limit.purge_failed` (sans valeur). Forme de la spécification (`DELETE … WHERE key IN (SELECT key … WHERE expires_at <= now() ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED)`). Raison du choix contre un point de sauvegarde : les verrous de la purge ne prolongent pas la transaction de l'incrément, et un échec de la purge ne peut pas laisser la transaction de l'incrément dans un état d'erreur.
5. **Lot** : 100 lignes. **Compartiment commun** : seuils d'une seule adresse IP de l'action (B3-PO-6).
6. **Type de marque de l'adresse e-mail** : `CanonicalEmail` (type de marque TypeScript, `string & { readonly __brand: "CanonicalEmail" }`), exporté de **`src/server/email.ts`** (nom retenu) avec `parseEmailAddress(entrée): { ok: true; email: CanonicalEmail } | { ok: false }` ; aucune autre fonction ne fabrique ce type (pas de conversion `as CanonicalEmail` hors de ce fichier : règle `no-restricted-syntax` sur `TSAsExpression` vers ce nom, testée dans `tests/unit/lint/`). Le limiteur, `src/server/auth` et le port d'envoi exigent ce type.
7. **Configuration** : `src/server/config/limites.ts` (dossier existant, à côté de `offer.ts`), valeurs de départ de 0008 (B3-PO-6) ; seuils réels : Q86, inchangée.

### B3-TL-7 — Journal : acceptée
1. **Module** `src/server/log.ts` (`import "server-only"`) : `logEvent(event, champs?)` écrit **une ligne JSON** par événement, par `console.log` (niveaux `info` et `warn`) ou `console.error` (niveau `error`) ; aucune dépendance, aucun niveau `debug`.
2. **Liste blanche par construction** : `event` est pris dans une union fermée de noms (au moins `config_missing`, `config_invalid`, `rate_limit.no_trusted_ip`, `rate_limit.purge_failed`, `rate_limit.rows_high`, puis en B3b `email.address_refused`, `email.transport_disabled`) ; les seuls champs admis sont `code` (un code de `API_ERROR_CODES`), `action` (même motif que B3-TL-6), `variable` (nom pris dans la liste fermée des variables connues de `src/server/env.ts`), `rule` (code de règle de B3-TL-1), `durationMs` et `rows` (entiers), `environment` (`local`, `ci`, `staging`, `production`) et `errorName` (`^[A-Za-z]{1,40}$`). Tout autre champ, et toute valeur qui ne suit pas le motif de son champ, est **retiré** avant l'écriture (le nombre de champs retirés est écrit dans `dropped`). Aucun message ni pile d'erreur n'est jamais écrit. C'est la forme retenue de « masqué ou retiré » : retirer, pas remplacer par une version tronquée.
3. Le journal de Better Auth (B3b) et les erreurs du port d'envoi passent par `logEvent` avec le seul nom d'erreur ; toute bibliothèque de journalisation reste une décision de dépendance (handover § 2).

### Amendement de 0007 : colonne `expires_at`, droits de `vadrouille_limiter`, plafond de lignes
1. **Migration additive de B3a** (`pnpm db:generate` après l'ajout dans `db/schema/auth.ts`) : `ALTER TABLE action_rate_limits ADD COLUMN expires_at timestamptz` ; `UPDATE action_rate_limits SET expires_at = window_start + interval '1 day'` (plus longue fenêtre connue, B9) ; `ALTER COLUMN expires_at SET NOT NULL` ; index `action_rate_limits_expires_at_idx` sur `expires_at`. 3. **Droits inchangés** : `vadrouille_limiter` garde `SELECT, INSERT, UPDATE, DELETE` sur la table (`0001_securite.sql` l. 196). Un droit de table couvre aussi les colonnes ajoutées ensuite : aucun `GRANT` nouveau, aucun autre rôle ne reçoit de droit, la politique `action_rate_limits_limiter` et la liste fermée des politiques `USING (true)` ne changent pas. Test `limitation: alerte au-delà du plafond de lignes` (`pnpm test:db`, seuil injecté, `ANALYZE` de la table par le rôle de test avant la lecture).
