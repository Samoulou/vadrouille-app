# 0007 — Application de la RLS : rôles, contexte de transaction, accès sans session

Statut : proposé · Date : 2026-10-08 (révisée le 2026-10-08 après la revue Tech Lead et Sécurité de la PR #27) · Décideur : Tech Lead (architecture, délégation « Qui décide quoi ») · Définitif sans veto de Samuel avant le 2026-10-10 pour sa partie technique. **L'accord tacite sous veto ne couvre pas les aspects juridiques** touchés par cette décision (conservation et purge des données, durées de conservation : Q27 ; données dérivées de Google : Q5, Q29) : ils restent soumis à une décision écrite de Samuel.

## Contexte
Le cadrage (§ 6.8, § 9) exige l'isolation par organisation, des permissions serveur doublées par la RLS et des tests d'isolation en CI. Plusieurs accès n'ont pas de session ou sortent du cas ordinaire : le lien privé (`/p/[token]`), le webhook de paiement, les étapes des workflows, la suppression de compte, la purge des coordonnées expirées et le limiteur des actions sans compte.

`FORCE ROW LEVEL SECURITY` soumet aussi le propriétaire des tables à la RLS. Une fonction `SECURITY DEFINER` s'exécute avec les droits de son propriétaire : si ce propriétaire est `vadrouille_owner` et qu'aucune politique ne le vise, la fonction ne voit **aucune ligne**. La revue de la PR #27 l'a relevé ; cette version fixe le mécanisme.

## Décision

### Rôles Postgres
Aucun rôle n'a `SUPERUSER` ni `BYPASSRLS`. Les rôles sans connexion (`NOLOGIN`) ne sont accessibles que par `SET LOCAL ROLE` depuis un rôle qui en est membre, ou, pour les propriétaires de fonctions, seulement par l'exécution de la fonction qu'ils possèdent.

| Rôle | Connexion | Usage | Droits |
|---|---|---|---|
| `vadrouille_owner` | non | Propriétaire du schéma et des tables | Aucune politique ne le vise : avec la RLS forcée, il ne lit ni n'écrit aucune ligne métier. Utilisé seulement par les migrations (via `vadrouille_migrator`) pour le DDL |
| `vadrouille_migrator` | oui | Exécute `db/migrations` en CI et au déploiement | Membre de `vadrouille_owner` et de lui seul ; jamais utilisé par l'application. Une migration de données ajoute une politique temporaire nommée `migration_<numéro>` et la retire dans la même migration (relue en revue) |
| `vadrouille_app` | oui | Actions serveur, adaptateur `api`, étapes de workflow | Non propriétaire ; droits table par table (tableau ci-dessous) ; jamais `UPDATE` ni `DELETE` sur `trip_versions`, `billing`, `usage_ledger` ; aucune écriture sur `billing` ni `entitlements` |
| `vadrouille_auth` | oui | Better Auth (décision 0008) | Tables d'authentification, `organizations`, `memberships`, `invitations` seulement ; aucune table métier |
| `vadrouille_share` | non | Lecture d'un voyage par lien privé | Accordé à `vadrouille_app` ; `SELECT` sur les **vues** de lecture partagée seulement (voir « Accès sans session ») |
| `vadrouille_webhook` | non | Traitement d'un événement de paiement | Accordé à `vadrouille_app` ; pris par `SET LOCAL ROLE` dans le seul cas d'usage du webhook ; `SELECT` sur `checkouts`, `trips`, `entitlements` ; `INSERT` sur `billing` et `entitlements` ; politique type (organisation courante, posée après `checkout_organization`) sur ces tables |
| `vadrouille_account_admin` | non | Suppression de compte | Accordé à `vadrouille_app` ; pris par `SET LOCAL ROLE` dans le seul cas d'usage `deleteAccount` ; seul rôle qui a `EXECUTE` sur `purge_organization_data` |
| `vadrouille_limiter` | non | Limiteur des actions sans compte (`structureBrief`, `suggestLodging`, lecture `/p/[token]`) | Accordé à `vadrouille_app` ; `SELECT, INSERT, UPDATE, DELETE` sur `action_rate_limits` seulement |
| `vadrouille_fn_share` | non | Propriétaire de `resolve_share_link` | `SELECT` sur les colonnes `token_hash`, `organization_id`, `trip_id`, `expires_at`, `revoked_at` de `share_links` ; politique `SELECT ... TO vadrouille_fn_share USING (true)` sur `share_links` seulement |
| `vadrouille_fn_checkout` | non | Propriétaire de `checkout_organization` | `SELECT` sur les colonnes `stripe_checkout_session_id`, `organization_id` de `checkouts` ; politique `SELECT ... TO vadrouille_fn_checkout USING (true)` sur `checkouts` seulement |
| `vadrouille_fn_purge` | non | Propriétaire de `purge_organization_data` | `SELECT` sur `memberships` ; `DELETE` sur les tables métier ; politiques `TO vadrouille_fn_purge USING (organization_id = app_current_org())` : la purge reste limitée à l'organisation de la transaction |
| `vadrouille_fn_coords` | non | Propriétaire de `purge_expired_coordinates` | `DELETE` sur `place_coordinates` ; politique `DELETE ... TO vadrouille_fn_coords USING (expires_at <= now())` |

Les rôles `vadrouille_fn_*` n'ont **aucun membre** (`pg_auth_members` vide pour eux) : personne ne peut `SET ROLE` vers eux. `current_user = 'vadrouille_fn_purge'` n'est donc vrai qu'à l'intérieur de la fonction de purge : c'est le critère non falsifiable du déclencheur d'ajout seulement (un `set_config` ne l'est pas, n'importe quel rôle peut le poser).

### Droits de `vadrouille_app` par table
| Droits | Tables |
|---|---|
| `SELECT, INSERT, UPDATE, DELETE` | `checklist_items` (élément retiré avec son étape), `preferences` (retrait de l'accord « Retenir mes goûts »), `stays` (logement modifié) |
| `SELECT, INSERT, UPDATE` | `trips`, `briefs` (insert seulement en pratique, ajout seulement par version), `generation_runs`, `research_runs`, `candidates`, `event_occurrences`, `feedback`, `preference_signals` (annulation par `status`), `share_links` (révocation par `revoked_at`), `checkouts`, `place_coordinates` (sans `DELETE` : purge par `purge_expired_coordinates`) |
| `SELECT, INSERT` | `trip_versions`, `usage_ledger` |
| `SELECT` | `billing`, `entitlements`, `organizations` (sa ligne), `memberships` (organisation courante), `users` (sa ligne : `id = app_current_user()`) |

Toute autre suppression passe par `purge_organization_data`. Un `DELETE` non accordé est refusé par les droits ; le test d'isolation vérifie les deux verrous (droits et RLS).

### RLS
`ENABLE` et `FORCE ROW LEVEL SECURITY` sur toutes les tables métier. Politique type, pour `vadrouille_app` :
`USING (organization_id = app_current_org()) WITH CHECK (organization_id = app_current_org())`, avec `app_current_org()` = `nullif(current_setting('app.organization_id', true), '')::uuid` et `app_current_user()` = `nullif(current_setting('app.user_id', true), '')::uuid` (fonctions `STABLE`, `search_path` fixé). Sans contexte, elles renvoient `NULL` : aucune ligne n'est lue ni écrite (échec fermé).

Les politiques testent **l'organisation**, pas le rôle `owner` ou `member` : au MVP, propriétaire et conseiller ont les mêmes droits sur les voyages de leur organisation. Les actions réservées au propriétaire (`exportAccount`, `deleteAccount`) sont vérifiées dans `src/server` **et** par `purge_organization_data` (contrôle de l'adhésion `owner` en base). La RLS double donc la vérification d'organisation ; elle ne double celle du rôle que pour la purge.

### Transmission de l'organisation
Chaque accès passe par `withOrg(ctx, fn)` (`src/server`), qui ouvre une transaction et exécute `select set_config('app.organization_id', $1, true), set_config('app.user_id', $2, true)` avant `fn`. Le paramètre `true` limite la valeur à la transaction : compatible avec les poolers en mode transaction (Supabase, Neon). `ctx` vient de la session (décision 0008), jamais d'un paramètre envoyé par le client.

### Fonctions `SECURITY DEFINER` : règles communes
Pour `resolve_share_link`, `checkout_organization`, `purge_organization_data` et `purge_expired_coordinates` :
1. propriétaire : le rôle `vadrouille_fn_*` dédié (`NOLOGIN`, `NOBYPASSRLS`, sans membre, propriétaire d'aucune table) ; jamais `vadrouille_owner` ;
2. `SET search_path = pg_catalog, pg_temp` dans la définition, et **tous** les objets nommés avec leur schéma (`public.share_links`, `public.app_current_org()`…) ;
3. `REVOKE ALL ON FUNCTION … FROM PUBLIC`, puis `GRANT EXECUTE` nominatif : `resolve_share_link` → `vadrouille_app` ; `checkout_organization` → `vadrouille_webhook` ; `purge_organization_data` → `vadrouille_account_admin` ; `purge_expired_coordinates` → `vadrouille_app` (tâche quotidienne). `ALTER DEFAULT PRIVILEGES … REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` dans la première migration ;
4. paramètres typés, aucun SQL dynamique ; résultats limités aux colonnes nécessaires.

### Accès sans session ou réservés
- *Lien privé* : `resolve_share_link(token_hash bytea)` renvoie `(organization_id, trip_id)` seulement si le lien n'est ni expiré ni révoqué. Le serveur ouvre alors une transaction, `SET LOCAL ROLE vadrouille_share`, pose `app.organization_id` et `app.trip_id`. `vadrouille_share` ne lit que des **vues** (`shared_trip`, `shared_trip_version`, `shared_checklist`, `shared_stays`), définies avec `security_barrier` et `security_invoker`, qui n'exposent que les colonnes de `SharedTrip` (ni `request_id`, ni `created_by`, ni `patch`, ni `validation_report`, ni `author_user_id`) ; leurs politiques exigent les deux réglages. Les colonnes de `stays` exposées suivent la réponse du Product Owner (handover § 17).
- *Webhook de paiement* : après vérification de la signature, le cas d'usage ouvre une transaction, `SET LOCAL ROLE vadrouille_webhook`, appelle `checkout_organization(stripe_checkout_session_id)`, qui renvoie l'organisation enregistrée à la création du paiement, pose `app.organization_id`, puis fait les contrôles et les écritures du handover § 9 **dans cette même transaction**. Les métadonnées de l'événement ne sont jamais crues seules.
- *Workflows* : l'entrée du workflow contient `organizationId` et `tripId`, écrits par le serveur après autorisation ; chaque étape ouvre sa propre transaction `withOrg`.
- *Suppression de compte* : `purge_organization_data(p_organization_id uuid)` est appelée seulement par le cas d'usage `deleteAccount` (`src/server/account/delete.ts` ; règle ESLint : la chaîne `purge_organization_data` n'apparaît que dans ce fichier et dans `db/`), dans une transaction `withOrg` puis `SET LOCAL ROLE vadrouille_account_admin`. La fonction refuse (exception, rien n'est supprimé) si `p_organization_id` est différent de `app_current_org()`, si `app_current_user()` est nul, ou si `app_current_user()` n'a pas l'adhésion `owner` de cette organisation. Elle supprime les lignes métier de cette organisation seulement (politiques limitées à `app_current_org()`). La purge des durées de conservation (Q27) n'utilisera pas cette fonction : elle fera l'objet d'une décision distincte quand Samuel aura fixé les durées.
- *Coordonnées expirées* : `purge_expired_coordinates()` supprime les lignes de `place_coordinates` dont `expires_at <= now()`, toutes organisations confondues, et rien d'autre (politique `DELETE` limitée à cette condition).
- *Limiteur* : table `action_rate_limits` (clé = HMAC de l'adresse IP et de l'action, fenêtre, compteur), sans `organization_id` (exception justifiée : actions anonymes), RLS activée et forcée, politique `TO vadrouille_limiter USING (true)`, aucun droit pour les autres rôles.

### Ajout seulement
`trip_versions`, `billing` et `usage_ledger` refusent `UPDATE` et `DELETE` : par les droits (aucun rôle applicatif n'a ces droits) et par un déclencheur `BEFORE UPDATE OR DELETE` qui lève une exception sauf si `current_user = 'vadrouille_fn_purge'` **et** l'opération est un `DELETE` (une mise à jour est toujours refusée). `TRUNCATE` est révoqué à tous les rôles applicatifs.

### Tests (CI, `pnpm test:db`)
- `schéma: RLS activée et forcée partout` : toute table du schéma `public` a `relrowsecurity` et `relforcerowsecurity`, sauf la liste des exceptions justifiées du handover (§ 6).
- `isolation: une organisation ne lit ni ne modifie les voyages d'une autre` : pour chaque table métier, deux organisations ; lecture, insertion, mise à jour et suppression croisées refusées sous `vadrouille_app` (refus par la RLS là où le droit existe, par les droits sinon).
- `rôles: aucun rôle ne contourne la RLS` (étend l'ancien test `rôles: le rôle applicatif ne contourne pas la RLS`) : pour **chaque** rôle `vadrouille_*` (`owner`, `migrator`, `app`, `auth`, `share`, `webhook`, `account_admin`, `limiter`, `fn_share`, `fn_checkout`, `fn_purge`, `fn_coords`) : ni `SUPERUSER` ni `BYPASSRLS` ; seul `vadrouille_owner` possède des tables ; `vadrouille_owner` (pris par `vadrouille_migrator`) lit zéro ligne sur chaque table métier remplie ; `vadrouille_migrator` n'est membre que de `vadrouille_owner` ; `vadrouille_auth` n'a aucun droit sur une table métier ; `vadrouille_share` n'a de droit que sur les vues partagées ; les rôles `vadrouille_fn_*` n'ont aucun membre ; la liste des rôles existants est comparée à celle-ci (un rôle ajouté sans test échoue).
- `fonctions: SECURITY DEFINER durcies` : pour chaque fonction `prosecdef`, `proconfig` contient `search_path=pg_catalog, pg_temp`, le propriétaire est le rôle `vadrouille_fn_*` attendu, `PUBLIC` n'a pas `EXECUTE`, et seuls les rôles prévus l'ont.
- `purge: vadrouille_app ne peut pas purger une autre organisation` : sous `vadrouille_app`, appel direct refusé (droit `EXECUTE` absent) ; sous `vadrouille_account_admin` avec le contexte de l'organisation A, `purge_organization_data(B)` lève une exception et ne supprime rien ; avec le contexte de A et un utilisateur `member`, refus ; avec le contexte de A et son `owner`, seules les lignes de A disparaissent.
- `versions: trip_versions est en ajout seulement`.
- `registres: billing et usage_ledger sont en ajout seulement` : sous chaque rôle applicatif, `UPDATE`, `DELETE` et `TRUNCATE` refusés ; un `SET ROLE vadrouille_fn_purge` est refusé (aucun membre) ; un `set_config` quelconque ne lève pas le déclencheur.
- `coordonnées: la purge ne supprime que les lignes expirées`.

## Conséquences
- Toute migration ajoute sa politique et son test d'isolation (règle du rôle `data`).
- Les permissions applicatives (rôle `propriétaire` ou `conseiller`) sont vérifiées dans `src/server` ; la RLS est le second verrou pour l'organisation, et pour le rôle seulement dans la purge.
- Un pooler en mode session reste compatible ; un pooler qui ne transmet pas `set_config` local est exclu.
- Tout nouveau rôle ou toute nouvelle fonction `SECURITY DEFINER` modifie cette décision et les tests `rôles` et `fonctions`.
