## 2. Méthode de détection
### 2.1 Analyse syntaxique
- Chaque fichier est lu par le **compilateur TypeScript** (`typescript`, déjà en `devDependencies` : aucun paquet ajouté), en mode TSX pour `tsx` et `jsx`. Aucune recherche de chaînes sur le texte brut, sauf pour les hôtes (2.5), qui portent sur les nœuds de chaîne de l'arbre.
- Les **commentaires** ne comptent pas. Les **positions de type** (annotations, `typeof X` dans un type, `import("…")` de type, déclarations `declare`) ne comptent pas comme usage d'une capacité, sauf les spécificateurs de module (2.2), qui comptent toujours, `import type` compris.
- Les **conversions de type sont transparentes** : `(window as T).x`, `globalThis!`, `(globalThis)` et `satisfies` sont analysés comme l'expression qu'ils enveloppent.
- **Texte littéral** : un littéral de chaîne, un gabarit sans substitution, ou le résultat replié d'une expression constante (2.5 : concaténation `+` de littéraux, gabarit dont toutes les substitutions sont des littéraux). Partout où une règle parle de clé ou d'argument « littéral », c'est ce sens : `o["con" + "structor"]` a la clé littérale `constructor`.

### 2.2 Spécificateurs de modules
- Sont relevés : `import … from`, `import type`, `export … from`, `export * from`, `import x = require("…")`, `import("…")` à spécificateur littéral, `require("…")` à spécificateur littéral (fichiers CommonJS admis par une ligne), et `import("…")` en position de type.
- Normalisation : un module intégré de Node doit être écrit **avec le préfixe `node:`** ; un nom intégré sans préfixe (`fs`, `http`) est traité comme un paquet tiers inconnu, donc refusé. Un spécificateur qui n'est ni relatif, ni `@/…`, ni un nom de paquet (`data:…`, `http(s):…`, `file:…`) n'appartient à aucune ligne et est refusé. Les sous-chemins comptent pour leur module (`node:dns/promises` relève de `node:dns` ; `drizzle-orm/pg-core` de `drizzle-orm`), sauf pour `next`, dont les sous-chemins sont énumérés un à un (section 6).
- Un spécificateur relatif ou `@/…` qui ne résout vers **aucun fichier suivi** fait échouer le test (échec fermé). Résolution : extension exacte, puis `.ts`, `.tsx`, `.mts`, `.mjs`, `.js`, `.d.mts`, `.d.ts`, puis `/index.*` ; `@/` vaut `src/`. Les fichiers `.css` et `.json` suivis sont des feuilles.

### 2.3 Identifiants, propriétés, objet global et réflexion
**Équivalences.** Dans toute cette section, un accès par crochets dont la clé est un texte littéral (2.1), chaînage optionnel compris (`o?.["x"]`), est traité exactement comme l'accès pointé du même nom : `o["sendBeacon"]` comme `o.sendBeacon`, `f["constructor"]` comme `f.constructor`. De même, chaque nom de propriété d'une **déstructuration d'objet** (déclaration, paramètre, affectation, boucle `for…of`), écrit en identifiant, en chaîne ou en nom calculé littéral, est traité comme une lecture de la propriété de ce nom : `const { constructor: F } = f` comme `const F = f.constructor`, `const { fetch } = window.parent` comme `window.parent.fetch`.

Sont relevés, en position de valeur (pas comme nom de propriété en création d'un littéral d'objet, pas comme nom de membre d'une classe) :
- les **identifiants** `fetch` (y compris en propriété abrégée `{ fetch }`), `WebSocket`, `XMLHttpRequest`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`, `eval`, `Function`, `require` (sauf `require("<littéral>")` dans un fichier CommonJS admis, traité comme un spécificateur en 2.2), `module` (CommonJS) ;
- les **propriétés refusées sur n'importe quel objet**, pointées, entre crochets littéraux ou déstructurées : `sendBeacon`, `getBuiltinModule`, `binding`, `_linkedBinding`, `dlopen`, `mainModule` ; les noms de capacité `fetch`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`, `eval`, `Function`, `require`, `process` (ce qui ferme `document.defaultView.fetch`, `window.parent.fetch`, `frames.fetch`, `module.require`) ; et `__proto__`, `__defineGetter__`, `__defineSetter__`, `__lookupGetter__`, `__lookupSetter__`. Sur `main` : aucune ;
- les **noms de l'objet global** `globalThis`, `global`, `self`, `window`. Leur usage est **admis** seulement sous ces formes : lecture ou écriture d'une propriété à nom littéral (`window.matchMedia`, `window["x"]`) qui n'est pas une propriété refusée ci-dessus ; opérande de `typeof` ; formes du régime des tests (section 4, formes 1 et 4). **Tout autre usage est une capacité** : accès calculé à clé non littérale (`globalThis[expr]`), **affectation à une variable ou à une propriété (alias)**, **passage en argument** (`Reflect.get(globalThis, …)`, `Object.getOwnPropertyDescriptor(globalThis, …)`, `Object.assign(…, window)`), retour de fonction, étalement, déstructuration (`const { fetch } = globalThis`), valeur par défaut, opérande de `for…in` (mineur 8) ;
- **`.constructor`** : admis seulement sous la forme `<expression>.constructor.name` en lecture, hors des zones sensibles et des fichiers hors programme (seul usage de `main` : `tests/unit/sejour-pages.test.tsx` l. 27). Toute autre forme est refusée : appel, `new`, gabarit étiqueté, affectation, argument, clause `extends`, accès à une autre propriété (`.constructor.value`, `.constructor.prototype`), déstructuration, crochets (2.6). C'est le chemin vers `Function` (et `AsyncFunction`, `GeneratorFunction`) depuis n'importe quelle fonction ;
- la **réflexion** : les identifiants `Reflect` et `Proxy`, refusés partout sous toute forme ; `Object` admis seulement comme objet d'un accès pointé (ni alias, ni argument, ni accès calculé) ; `Object.getPrototypeOf`, `Object.setPrototypeOf`, `Object.getOwnPropertyDescriptor`, `Object.getOwnPropertyDescriptors`, `Object.getOwnPropertyNames`, `Object.getOwnPropertySymbols` et `Object.defineProperties`, refusés partout ; `Object.defineProperty`, admis seulement dans un fichier de test hors zone sensible, avec un premier argument qui n'est ni un nom de l'objet global ni `process`, et une clé littérale qui n'est pas un nom interdit (2.6) (seul usage de `main` : `src/features/voyage/use-client-now.test.tsx` l. 16, `Object.defineProperty(document, "visibilityState", …)`). Sont donc refusés `Reflect.get(fn, "constructor")`, `Object.getOwnPropertyDescriptor(fn, "constructor")`, `Object.getOwnPropertyDescriptors(Object.getPrototypeOf(fn))` (énumération du prototype d'une fonction) et `const O = Object`. `Object.keys`, `Object.entries`, `Object.values`, `Object.assign`, `Object.freeze`, `Object.fromEntries`, `Object.hasOwn` restent admis (`src/prototype/programme-reduit.ts` l. 178 : `Object.hasOwn(valeur, "__proto__")`, où `"__proto__"` est un argument, pas un accès).

Le contrôle ne fait **aucune analyse de portée** : une variable locale nommée `fetch` est refusée comme le `fetch` global. C'est voulu (plus simple, sans faux négatif) ; aucun fichier de `main` n'en souffre.

**Limite assumée : objet global du navigateur.** Dans le code exécuté par le navigateur, l'objet global reste atteignable par des propriétés du DOM (`document.defaultView`, `window.parent`, `frames`, `contentWindow`) et énumérable (`Object.values(document.defaultView)`), ce qui donne `fetch` sans le nommer. Le régime ferme les formes nommées (ci-dessus) mais pas l'énumération d'objets du DOM. C'est accepté parce qu'aucune variable serveur n'atteint le navigateur (test « clé côté serveur » de P0r1 ; seule `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`, publique, y est lue) et que les chargements du navigateur par le DOM sont hors périmètre. Côté serveur (Node), il n'y a pas de DOM : l'objet global n'est atteignable que par les noms de cette section et par `process` (section 5), tous fermés.

### 2.4 Contournements refusés partout (sans exception possible)
`import()` et `require()` à spécificateur non littéral ; `import.meta.resolve` ; `import.meta.env` ; `eval` ; `new Function` et `Function(…)` ; `.constructor` hors de la forme `.constructor.name` (2.3) ; la réflexion refusée par 2.3 ; l'instruction `with` ; `setTimeout` et `setInterval` dont le premier argument n'est pas une fonction (dans le programme TypeScript : type sans signature d'appel ; ailleurs : autre chose qu'une fonction fléchée, une expression `function` ou un identifiant), forme qui évalue une chaîne dans le navigateur (sur `main` : 6 appels, tous avec une fonction fléchée ou un identifiant de fonction) ; `process.binding`, `process._linkedBinding`, `process.dlopen`, `process.mainModule`, `process.getBuiltinModule` ; `module.require`, `module.createRequire` ; `createRequire` de `node:module` hors de la seule exception nominative de `src/lib/large-screen.test.tsx` ; un accès calculé refusé par la section 2.6 ; tout texte (2.5, après normalisation) qui contient `/proc/` (lecture de `/proc/self/environ` : mineur 4 de la revue du head `2eecd59` de #180) ; tout texte qui désigne un fichier d'environnement, `(^|/)\.env(\.[a-z0-9.-]+)?$`, sauf `.env.example` (lu par `tests/unit/google-regles.test.ts` et cité par `tests/unit/debloquer-regles.test.ts` sur `main`). ### 2.5 Hôtes : normalisation, expressions régulières, gabarits
- **Textes examinés** : littéraux de chaîne, gabarits sans substitution, chaque segment (`quasi`) d'un gabarit, texte JSX et valeurs d'attributs JSX, corps des littéraux d'expression régulière, et le **résultat replié** des expressions constantes : concaténation `+` de littéraux, gabarit dont toutes les substitutions sont des littéraux (`` `${"openrouter"}.ai` `` donne `openrouter.ai`). Les spécificateurs de modules sont exclus (2.2 les traite).
- **Normalisation** de chaque texte, dans cet ordre : forme NFKC ; minuscules ; décodage de `%2e` en `.` ; dans un corps d'expression régulière et dans les arguments de `new RegExp(…)`, retrait des échappements (`\.` donne `.`, `\/` donne `/`) et remplacement de la classe `[.]` par `.` ; retrait d'un point final de nom pleinement qualifié.
- **Hôtes surveillés** : `openrouter.ai`, `googleapis.com` et `ai-gateway.vercel.sh` (chemin de l'AI Gateway, à fermer avec la règle de P0r1 sur l'AI SDK), chacun avec ses sous-domaines. Correspondance par **limite d'étiquette** : `(?<![a-z0-9-])(?:[a-z0-9-]+\.)*(openrouter\.ai|googleapis\.com|ai-gateway\.vercel\.sh)(?![a-z0-9-])`.
- **Fragments** : les étiquettes isolées `openrouter` et `googleapis`, `(?<![a-z0-9])(openrouter|googleapis)(?![a-z0-9])`, sont aussi relevées, pour attraper une concaténation faite à l'exécution (`base + ".ai"`). Une ligne d'hôte couvre les fragments relevés dans le même texte.
- **Limite** : un hôte calculé autrement (codes de caractères, base64, chaîne venue d'un fichier) échappe à cette recherche. Ce risque est résiduel et accepté : le contrôle principal est celui des capacités (2.3, 2.4, `next` en section 6 et `next.config.ts` en section 7), sans lesquelles aucune requête ne part du serveur.

### 2.6 Accès calculés (ajout du CEO 3)
La règle ne se limite ni à l'objet global, ni à la forme littérale `.constructor` : `(() => {})[k]` avec `k` qui vaut `"constructor"` donne `Function`, quel que soit le nom de `k` et même si `Symbol` est redéclaré (`const Symbol = { c: "constructor" }`, puis `(() => {})[Symbol.c]`, cas du bloquant 1 de la revue du head `2eecd59` de #180). Sont des **accès calculés** : `o[k]` (lecture, écriture, appel, chaînage optionnel compris), le nom calculé d'une déstructuration (`const { [k]: v } = o`) et l'élément de reste d'une **déstructuration d'objet** (`const { a, ...r } = o`). Ne sont pas des accès calculés : le nom calculé d'un **littéral d'objet** en création (`{ [k]: v }`), qui écrit sur un objet neuf et ne lit rien ; le reste d'une **déstructuration de tableau** (`const [command, ...args] = process.argv.slice(2)`, `scripts/ci/release-note.mjs` l. 36), qui ne lit que des indices.

**Noms interdits** : `constructor`, `prototype`, `__proto__`, `__defineGetter__`, `__defineSetter__`, `__lookupGetter__`, `__lookupSetter__`, `caller`, `callee`, `arguments`, `call`, `apply`, `bind`, `process`, `env`, `fetch`, `require`, `eval`, `Function`, `globalThis`, `getBuiltinModule`, `binding`, `_linkedBinding`, `dlopen`, `mainModule`, `sendBeacon`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`.

**Partout** (zones sensibles, fichiers hors programme et reste du dépôt) : une **clé littérale** (2.1) entre crochets qui est un nom interdit est refusée (bloquant 2 de la revue du head `a8538fb` : `(() => {})["constructor"]("return fetch")()`, `x["getBuiltinModule"]`, `process["binding"]`, `navigator["sendBeacon"]`). Sur `main` : aucune. Les noms de déstructuration écrits en clair suivent 2.3 (`const { constructor: F } = f` y est refusé ; `{ env }`, paramètre de `e2ePort` dans `scripts/e2e-port.mjs` l. 33, reste admis).

**Zones sensibles** (section 1) et **fichiers hors programme** (section 1 ; sur `main`, 9 fichiers `.mjs` ; plus tard `scripts/p0/**`) : règle fermée de #180 (décision issuecomment-6132707686, point 1). Une clé n'est admise que si elle est un texte littéral ou un littéral de nombre, et pas un nom interdit, ou `Symbol.iterator`, `Symbol.asyncIterator`, `Symbol.toStringTag`, `Symbol.hasInstance` **et** qu'aucun identifiant `Symbol` n'est lié dans le fichier (variable, paramètre, import, classe, fonction). Le nom calculé et le reste d'une déstructuration d'objet sont refusés. Seule exception, nominative (section 5) : `process.env[SERVER_LOG_ENV]` dans `scripts/serve-standalone.mjs` l. 24. Sur `main` : aucune zone sensible n'existe ; dans les fichiers hors programme, ce `process.env[SERVER_LOG_ENV]` est le seul accès calculé à clé non littérale, et il n'y a ni nom calculé ni reste de déstructuration d'objet (vérifié).

**Reste du dépôt** : la clé est jugée par son **type statique**, donné par le vérificateur de types de `typescript` sur le programme de `tsconfig.json` (P0c-TL-5), conversions de type retirées de la clé **et** de l'objet avant de demander le type (2.1). Un paramètre de type, un type conditionnel ou un accès indexé générique est jugé par sa **contrainte de base** (celle que donne le vérificateur) ; sans contrainte, il est refusé. Une clé non littérale est admise si **l'objet** n'est ni appelable ni constructible (aucune signature d'appel ni de construction), ni l'objet global, ni `process` (type qui comprend `typeof globalThis`, `Window` ou `NodeJS.Process`) — sauf la ligne de `src/adapters/simulation.ts` (section 3) — **et** si le type de la clé est :
1. numérique ;
2. une union de littéraux de chaîne et de nombres dont aucun n'est un nom interdit ;
3. `string`, **seulement** si l'objet a une signature d'index de chaîne (`Record<string, T>`, `{ [k: string]: T }`) ;
4. un `unique symbol` déclaré dans le même fichier par `const X = Symbol.for("<littéral>")` ou `Symbol("<littéral>")`, `Symbol` n'étant lié nulle part dans le fichier ; ou l'un des quatre symboles bien connus ci-dessus aux mêmes conditions.

Tout autre type est refusé, en particulier `any`, `unknown`, `string` sur un objet sans signature d'index, toute clé non littérale sur une fonction ou une classe (même numérique ou d'union sûre), et un littéral interdit. Le reste d'une déstructuration d'objet est admis hors des zones sensibles et des fichiers hors programme (il ne copie que des propriétés propres énumérables ; `main` l'utilise pour les composants). Un `Symbol` lié dans un fichier fait refuser tout accès dont la clé passe par lui.

Relevé sur `main` (`40b6738`, vérificateur de types sur `tsconfig.json`) : 156 accès ou noms calculés à clé non littérale dans le programme TypeScript. 111 accès à clé numérique ou à union de littéraux sans nom interdit (cas 1 et 2), dont 2 à clé générique jugée par sa contrainte (`src/features/creation/BriefReview.tsx` l. 379, `F extends ChipField`, et l. 399, type conditionnel sur `F` ; contraintes : unions de littéraux) ; 14 accès à clé `string` sur un `Record<string, …>` non appelable (cas 3, dont `src/features/sejour/programme.ts`, `src/adapters/mock.ts`, `src/i18n/index.ts`, `src/features/creation/BriefReview.tsx` l. 99) ; 2 accès à `unique symbol` (cas 4, `holder[REGISTRY_KEY]` de `src/adapters/simulation.ts`, `REGISTRY_KEY = Symbol.for(…)`, sur l'alias de `globalThis` de sa ligne) ; 28 noms calculés de littéraux d'objet en création (dont `[SERVER_LOG_ENV]` de `playwright.config.ts`) ; 1 nom calculé en position de type (`src/adapters/simulation.ts` l. 97, hors analyse, 2.1). Hors du programme : le seul `process.env[SERVER_LOG_ENV]` ci-dessus. Aucune déstructuration à nom calculé ; 9 restes de déstructuration d'objet, tous dans le programme et hors zone. Aucun accès calculé sur un objet appelable ou global hors de la ligne de `simulation.ts`. **Tous admis**, sans autre ligne. Le même calcul sur `b2c181e` donne 115 (82, 13, 2, 17 et 1), chiffres de la correction 1.

**Limite assumée.** Hors des zones sensibles et des fichiers hors programme, un type peut mentir : valeur `any`, conversion faite ailleurs que dans l'expression de la clé ou de l'objet (dans une fonction, une variable annotée : `const r: Record<string, unknown> = f as unknown as Record<string, unknown>`, puis `r[k]`), déclaration ambiante (`declare`, fichiers `.d.ts` et `.d.mts`), directive `@ts-ignore` ou `@ts-expect-error`. La règle ESLint `@typescript-eslint/no-explicit-any` du dépôt réduit ce cas sans le fermer ; les fichiers de déclaration et `tsconfig*.json` sont des chemins gardés (section 8). Le risque reste acceptable parce que les zones sensibles, où vivent les clés et les modules de capacité, et les fichiers hors programme appliquent la règle fermée, qu'il faut mentir à la fois sur l'objet et sur la clé (un objet appelable est refusé quel que soit le type de la clé), et que la section 5 interdit hors de `src/server/env/` toute lecture d'un nom secret.

## 4. Régime des tests
**Fichiers de test** : `*.test.ts`, `*.test.tsx`, `*.spec.ts` et tout fichier sous `tests/` (utilitaires compris). Un fichier de test ne reçoit **aucune** capacité par principe ; il reçoit seulement les formes suivantes, sans ligne nominative sauf mention, parce qu'elles **remplacent** une capacité par un double ou n'en ouvrent aucune :
1. `vi.spyOn(globalThis, "<littéral>")`, `vi.spyOn(window, "<littéral>")`, `vi.stubGlobal("<littéral>", <expr>)` et `vi.unstubAllGlobals()` : c'est ainsi qu'un test remplace le `fetch` global par un double. Le premier argument de `vi.spyOn` et le nom de `vi.stubGlobal` sont des littéraux. Quand ce littéral est un nom de capacité de 2.3 (`fetch`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `Worker`, `SharedWorker`, `importScripts`, `eval`, `Function`, `require`) ou `process`, `vi.spyOn(…)` doit être **immédiatement** suivi d'un remplacement (`.mockImplementation(…)`, `.mockResolvedValue(…)`, `.mockRejectedValue(…)` ou `.mockReturnValue(…)`) : un espion sans remplacement laisse passer l'appel réel (mineur 7 de la revue du head `a8538fb`). **Seule forme nominative**, soumise à « ligne inutile » : `src/analytics/events.test.ts` l. 112, `const fetchSpy = vi.spyOn(globalThis, "fetch")` sans remplacement, qui vérifie qu'aucun appel n'a lieu (`expect(fetchSpy).not.toHaveBeenCalled()`). Risque accepté par écrit : le code testé (`consoleRecorder`, `noopRecorder` de `src/analytics`) ne peut pas appeler `fetch` (2.3), et les tests tournent sans clé (« Clés »). De même, un espion remplacé puis restauré (`mockRestore`) redevient un passe-plat : risque résiduel accepté pour la même raison.
2. `vi.mock("<spécificateur>", <fabrique>)` et `vi.doMock(…)` d'un module à capacité (doubles de `node:http`, `node:https`, `node:net`, `node:dns`, `node:dns/promises`, `undici`…), à condition que le spécificateur soit littéral et que la fabrique n'appelle **ni** `importOriginal`, **ni** `vi.importActual`, **ni** `vi.importMock`. Le module réel n'est donc jamais chargé ; un `import("<module à capacité>")` écrit dans la fabrique est un import réel, refusé sans ligne (2.2). **Cette restriction ne vise que les modules à capacité** (section 3) et les fichiers qui en importent un, directement ou par fermeture transitive : `vi.mock` d'un module sans capacité avec `importOriginal`, et `vi.importActual` d'un tel module, sont admis sans ligne. 3. `vi.stubEnv("<NOM>", <valeur>)` et `vi.unstubAllEnvs()`, avec un nom **littéral** qui n'est pas un nom secret (section 5). Cette forme suit **la seule section 4** : elle n'a pas de ligne dans le tableau `process.env` de la section 5 et n'est pas soumise à la règle « ligne inutile ». Une seule forme nominative, soumise à cette règle : `tests/unit/accueil.test.tsx`, `vi.stubEnv(name, "production")` (l. 97), où `name` est le paramètre du rappel de `it.each([["VERCEL_ENV"], ["VADROUILLE_ENV"]])` ; le test vérifie que la table est un littéral qui ne contient que ces deux noms. ### Découpage et comparaison (mineurs des revues `fc54aae` et `a8538fb`, ajout du CEO 1)
La même procédure s'applique aux scripts de `package.json`, aux workflows (dans la mesure écrite à « Workflows »), aux instructions `RUN` et `CMD` du `Dockerfile`, à toute valeur de `NODE_OPTIONS` où qu'elle soit posée, et à `process.execArgv` et `NODE_OPTIONS` lus à l'exécution par `src/server/env/egress.ts` de P0r1, qui reprend la liste commitée du régime (`tests/unit/confinement/donnees/options-interdites.json`, nom proposé) :
1. **Découpage en jetons** : (a) chaque `\` suivi d'une fin de ligne est retiré ; (b) la forme exec du `Dockerfile` (`CMD ["node", "server.js"]`) est lue comme un tableau JSON, chaque élément étant un jeton ; (c) ailleurs, les guillemets simples et doubles sont **retirés avant** le découpage, si bien que le contenu d'une chaîne est découpé comme le reste (`sh -c "node -e x"` donne `sh`, `-c`, `node`, `-e`, `x`) ; (d) séparateurs : les blancs et chacun des caractères `;`, `&`, `|`, `(`, `)`, `<`, `>` et l'accent grave. Une **commande** se termine à `;`, `&`, `|`, `(`, `)`, à l'accent grave ou à une fin de ligne. Aucune comparaison par sous-chaîne : `-p` ne correspond pas à `--project`, ni à `mkdir -p` (ci-dessous).
2. **Jeton `node`** : un jeton dont le dernier segment après `/` est `node` ou `nodejs` (`/usr/bin/node` compris). **Jetons examinés comme options de Node** : **tous** les jetons qui commencent par `-` entre ce jeton et la fin de sa commande, arguments du script compris (plus strict : l'examen ne s'arrête pas au premier jeton sans tiret, ce qui ferme `node --conditions react-server -r x s.mjs`), et chaque jeton de la valeur de `NODE_OPTIONS`. Les options des autres commandes (`playwright test --project=…`, `mkdir -p`) ne sont pas des options de Node.
3. **Normalisation** de chaque option de Node, dans cet ordre : (a) un jeton qui commence par un seul `-` et compte plus d'une lettre avant un éventuel `=` est développé lettre à lettre, comme Node regroupe les options courtes (`-pe` donne `-p` et `-e`) ; (b) on garde la partie avant le premier `=` (`--require=x` donne `--require`) ; (c) on remplace chaque `_` par `-` (Node accepte `--tls_cipher_list` pour `--tls-cipher-list`, `--use_openssl_ca`, `--insecure_http_parser`) ; (d) un préfixe `--no-` est retiré (`--no-insecure-http-parser` est comparé comme `--insecure-http-parser`, et refusé : une option interdite l'est dans ses deux sens).
4. **Comparaison de l'option entière** à la liste ; une entrée terminée par `*` (`--tls-*`, `--openssl-*`, `--inspect*`, `--env-file*`) est un préfixe de l'option normalisée (`--inspect-brk`, `--inspect-port`, `--inspect-wait`, `--env-file-if-exists` compris).
5. **Mots interdits** : comparés par jeton entier, `pnpm dlx` et `npm exec` comme deux jetons consécutifs, sur **tous** les jetons des scripts de `package.json` et des instructions `RUN` et `CMD` du `Dockerfile` **seulement** (les workflows ont leurs propres règles, ci-dessous).

Sur `main`, aucun jeton n'est refusé : les seuls `node` des scripts (`start`), des workflows (`release-note.mjs` deux fois, `techlead-gate.mjs` une fois) et du `Dockerfile` (`CMD ["node", "server.js"]`) ne sont suivis d'aucun jeton qui commence par `-` jusqu'à la fin de leur commande, `NODE_OPTIONS` n'apparaît nulle part, et ni `package.json` ni le `Dockerfile` ne contiennent un mot interdit. B1 (#188) ajoutera `--conditions=react-server` et `--disable-warning=…`, qui ne sont pas interdits.

## 8. Garde des chemins : `CODEOWNERS` et contrôle de chemins
### Chemins gardés
Les tests, listes et données du régime (`tests/unit/confinement/**`, dont `donnees/*.json`), `tests/support/**`, les fichiers nommés dans une ligne de capacité ou de `process.env` (lus dans la liste, dont `scripts/e2e-server-log.mjs`), les modules de capacité de P0r1 et `src/research/ip-guard.ts`, `src/research/fetch-page.ts`, `src/server/env/**`, `src/server/composition/**`, `package.json`, `pnpm-lock.yaml`, `.npmrc`, `pnpm-workspace.yaml`, `.github/workflows/**`, `.github/CODEOWNERS`, `scripts/ci/**`, `Dockerfile`, `.dockerignore`, `playwright.config.ts`, `vitest.config.mts` (et toute autre configuration de Vitest), `next.config.ts`, `tsconfig*.json` (programme et options du vérificateur de types de la section 2.6), les fichiers de déclaration `**/*.d.ts` et `**/*.d.mts` (limite de la section 2.6), `eslint.config.mjs`, `eslint-rules/**`, `middleware.*`, `instrumentation.*`. La liste est commitée dans `tests/unit/confinement/donnees/chemins-gardes.json` (nom proposé), lue par le contrôle de chemins dans sa version de `main`.

### Mécanisme
1. **`CODEOWNERS`** (`.github/CODEOWNERS`) sur ces chemins, propriétaire `@Samoulou`. Il rend les chemins visibles dans chaque PR ; il ne bloque rien sans réglage de la protection de `main` (P0-Q21).
2. **Contrôle de chemins** exécuté par un workflow `pull_request_target` : version du workflow et du script prise sur `main`, **sans extraction du code de la PR**, permissions `contents: read` et `pull-requests: read`, aucun secret. La liste des fichiers modifiés est lue par l'API (`GET /pulls/{n}/files`, paginée) ; au-delà de la limite de l'API (3 000 fichiers) ou en cas d'erreur, le contrôle échoue. Il échoue si un chemin gardé change et que le verdict lu (ci-dessous) manque. La forme du script et du workflow est une décision du Tech Lead (P0c-TL-3). C'est une PR de workflow : elle attend `owner-approved`, posé par Samuel (Q245, T18).
3. **Événements** (bloquant 3 de la revue du head `a8538fb`) : `pull_request_target` avec les types `opened`, `synchronize`, `reopened`, `labeled` et `unlabeled`, comme `techlead-gate.yml`. `synchronize` relance le contrôle à chaque push : le head change, la revue précédente ne vaut plus, le contrôle échoue jusqu'à la revue du nouveau head. `labeled` le relance **après** la revue : un commentaire ne déclenche pas `pull_request_target`, mais l'étape 6 de R2 pose `techlead-approved` ou `changes-requested` juste après avoir publié la revue (étape 5), sous le compte `Samoulou`, ce qui déclenche l'événement (un libellé posé avec `GITHUB_TOKEN` ne le ferait pas, 0023 § 4.8). Sans `labeled`, le contrôle ne se relancerait pas après la revue et resterait rouge.

### Verdict lu : format exact (bloquant 2 de la revue `fc54aae`, bloquant 3 de la revue `a8538fb`)
Le contrôle lit les commentaires de la PR (`GET /issues/{n}/comments`, paginé) et ses revues (`GET /pulls/{n}/reviews`, paginé), comme `techlead-gate` (0023 § 4.3), et ne garde que les corps dont l'**auteur** a le login `Samoulou` (dépôt public : un commentaire d'un tiers qui imite le format est ignoré). Parmi eux, il prend la **revue consolidée la plus récente** (date de création, ou de soumission pour une revue), au sens de `techlead-gate` : tout corps qui contient le titre reconnu par l'expression `CONSOLIDATED` de `scripts/ci/techlead-gate.mjs` (l. 12, titre n'importe où, tiret quelconque), quel que soit son head. Le contrôle passe seulement si **cette** revue :
1. a pour **première ligne** exactement `## Revue consolidée — head ` suivi du sha court entre accents graves, soit l'expression `` ^## Revue consolidée — head `([0-9a-f]{7})`$ `` (tiret cadratin U+2014, espaces simples ; fin de ligne `\r` retirée) ;
2. porte un sha égal aux 7 premiers caractères du **head courant** de la PR ;
3. contient une ligne qui, fin de ligne `\r` et blancs de fin retirés, est **exactement** :

```
- securite : **approuvé**
```

soit `^- securite : \*\*approuvé\*\*$` (tiret et espace en début de ligne, nom de rôle `securite` sans accent, une espace de chaque côté du deux-points, `approuvé` en minuscules avec `é` U+00E9, en gras). Une précision du rôle va **à la ligne suivante**, jamais sur cette ligne. Toute autre forme (`**Sécurité** : approuvé`, `securite — **approuvé**`, « Rôles consultés : … securite — **approuvé** ») ne compte pas.

Le contrôle échoue donc si la revue consolidée la plus récente est d'un autre head, si sa première ligne n'a pas la forme exacte (même si une revue plus ancienne l'avait), ou si elle ne porte pas la ligne (changements demandés, `securite : non consulté`), même si une revue plus ancienne du même head la portait. Prendre la plus récente au sens large de `techlead-gate`, et non la plus récente au format strict, ferme le cas d'une revue récente mal titrée qui laisserait compter une approbation plus ancienne. Le contrôle reste plus strict que `techlead-gate` (première ligne exacte) : une revue consolidée mal formée le fait échouer, ce qui est voulu (échec fermé). Les revues consolidées de #193 (heads `fc54aae` et `a8538fb`) ont déjà cette première ligne exacte. Une modification ultérieure d'un commentaire n'est pas détectée (date de création) : c'est le même compte (« Indépendance »).

**Constat.** Ce format n'existe pas encore dans les textes : 0019 § 3.2 et 0023 § 1 ne fixent aucune ligne de verdict par rôle ni la première ligne exacte (l'étape 5 de R2 dit seulement « titré »), et les revues consolidées de `main` emploient plusieurs formes (« - securite : non consulté (…) » dans les revues de #193, « **Rôles consultés** : tech-lead — **approuvé** » dans #182, « - **Sécurité** : changements demandés » dans #180). Surtout, l'étape 2 du prompt de la routine R2 (0023 § 1) n'appelle `securite` que si la PR touche `db/`, `src/ai/`, `src/research/`, l'authentification ou des secrets : sur `package.json`, un workflow, `scripts/ci/**`, le `Dockerfile`, une configuration, `tests/unit/confinement/**` ou `src/server/composition/**`, aucune ligne ne serait produite et le contrôle échouerait toujours. Le prompt d'une routine se règle hors du dépôt et relève de Samuel (0023 § 1, « Samuel le colle dans la routine Revue ») : cette spécification **ne le modifie pas**. Elle pose la modification comme question, **P0c-Q2** (« Questions ouvertes »), avec le texte proposé, et rend P0c2 dépendante de la réponse (« Découpage et ordre »).

**Déclencheur indépendant de R2 : examiné, non retenu.** Aucun déclencheur réaliste ne se passe de Samuel : un workflow ne peut pas lancer un agent `securite` sans clé d'API (compte et dépense externes, réservés à Samuel) ; les prompts de R1 et R3 se règlent aussi hors du dépôt ; une revue Sécurité faite par le rôle qui pousse, dans sa propre session, ne serait pas une revue distincte et ne serait pas la revue consolidée qu'exigent 0019 et 0023. Le studio retient donc la question à Samuel.

### Indépendance (mineur 11)
